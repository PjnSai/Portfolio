# Decisions

Short record of choices made while building, with the reason. Newest last.

## Phase 0

- **Django 5.2 (LTS) on Python 3.12.** The spec asks for the current LTS release. Python 3.12 matches the local toolchain and is supported by 5.2.
- **Python dependencies pinned with hashes** (`pip-compile --generate-hashes`; edit `requirements*.in`, then recompile). An altered package fails the install rather than being used.
- **No database URL library.** `DATABASE_URL` is parsed with the standard library in `config/settings.py`; one dependency fewer.
- **Redis client not installed yet.** Nothing uses it until rate limiting arrives in phase 1.
- **API denies by default.** The default DRF permission is `IsAuthenticated`; public endpoints opt in with `AllowAny`. JSON renderer and parser only, so there is no browsable API.
- **No default secret key.** The API refuses to start without `DJANGO_SECRET_KEY`. Tests set their own in `tests/settings.py`.
- **Web image is distroless** (non-root, no shell). **API image is `python:3.12-slim`** running as a numeric non-root user on a read-only filesystem. It still contains a shell; moving it to a shell-less base is left for the hardening phase.
- **Gunicorn control socket disabled.** It is not needed and would require a writable home directory.
- **Base images are pinned by tag for now.** Pinning by digest is left for the hardening phase; Dependabot watches them meanwhile.
- **No web fonts or placeholder styling.** Design work starts in phase 3.
- **End-to-end tests run against the standalone build**, the same server the container runs.
- **`/healthz` on Cloud Run.** The Google front end may intercept some paths ending in `z` on `*.run.app` URLs. To be confirmed in phase 7 before health checks rely on it from outside.

## Phase 1

- **No Django auth, sessions or admin apps.** Passkeys and sessions live in `core`, so there is no password table and no code path that could accept one.
- **Cloudflare Access is checked by the API itself**, on every admin request and before the URL is resolved. The API does not trust that a request came through Cloudflare; it verifies the signed token (RS256 only, audience, issuer, owner email). Unknown admin paths therefore look the same as known ones.
- **One place decides admin authorisation.** Every admin view is wrapped with `admin_route(level)`; the guard refuses any admin URL without a declared level, so a new route is denied until someone chooses its level.
- **CSRF: three independent checks.** State-changing requests need an exact `Origin`, `Sec-Fetch-Site: same-origin`, and a CSRF token. (Token handling replaced below, under "Django built-ins".)
- **Session token is random, stored as SHA-256.** A plain hash is enough because the token is 256 random bits; there is nothing to brute-force.
- **Passkey confirmation lasts five minutes** and issues a new session token. It is not consumed by one action, so several vital actions can be requested in one sitting.
- **Sign-in failures are indistinguishable.** No credential list is sent, and an unknown passkey is still verified against a throwaway key so the work is the same.
- **Rate-limit counters in Redis, cool-downs in Postgres.** A cool-down must survive a Redis restart; a counter need not. Addresses are stored only as a keyed hash.
- **The global cool-down never blocks a valid passkey.** Failures from many addresses start it. It closes bootstrap and turns every failed sign-in into a 429, but `login/options` stays open and a correct passkey signs in. Otherwise anyone able to reach the sign-in route could lock the owner out for as long as they kept failing. During it all failures get the same 429 after the same signature check, so it reveals nothing about which passkeys exist. A client's own cool-down still refuses even the right passkey, and still ends after 15 minutes.
- **The 503 for a missing dependency is admin only.** The guard uses neither the database nor Redis for a public request and does not convert errors raised by public views. Public reads get their own fail-static handling in phase 3.
- **Vital actions: fixed 24-hour wait, then a 7-day window.** The delay is a constant on the server; fields the client sends for it are ignored. An action not run within seven days of maturing expires. Cancelling needs only a session, so a cancel is always easier than a run.
- **A vital action is refused if the owner cannot be told.** This includes the case where no notifier is configured. The request, its audit entry and the notice succeed or fail together. A new passkey is likewise undone if its notice fails.
- **Notifiers are chosen by the `NOTIFIERS` setting** (comma-separated dotted paths). `core.notify.LogNotifier` writes notices to the log and is the only one shipped so far; an email notifier arrives in phase 5. Until then the notice is only as out-of-band as the log alerts are.
- **Permanent delete covers messages only**, by allow-list (sections and items from the trash joined in phase 2A). Media and CV files join when their stored objects can be removed with them (phases 2 and 4). Auth and audit tables can never be named.
- **Adding a passkey is two steps after the wait**: options, then run with the new credential. A failed registration leaves the action ready to try again.
- **Audit listing is paged by sequence number**, newest first, at most 100 per page. Unknown or repeated query parameters are refused rather than ignored.
- **Audit chain limit.** Removing the newest entries leaves a shorter chain that still verifies. Catching that needs the latest sequence number and hash kept somewhere else; planned with backups in phase 7.
- **Web CSP uses a per-request nonce**, set in `web/proxy.ts` (the Next.js 16 name for middleware) with no matcher, so every response carries the headers. Next.js reads the nonce from the request and adds it to its own tags. The cost: every page is rendered per request (`connection()` in the root layout), so pages cannot be cached at the edge as they are. To be revisited in phase 3, when public pages need caching; hash-based CSP is the likely answer.
- **No `upgrade-insecure-requests` in the CSP.** HSTS does that job, and the directive would break tests against the local HTTP server.
- **`npm run typecheck` runs `next typegen` first.** The layout uses a generated type, and CI type-checks before it builds.
- **CI runs Postgres and Redis as job services**, the same major versions as Docker Compose. Their password is a fixed throwaway value: the services exist for one job and hold no real data. The database role tests need a superuser to create roles.
- **One owner row, enforced by the database.** `admin_owner` holds a single row made by a migration: a unique boolean that a check constraint pins to true. The app login has SELECT and column-level UPDATE only, so a bug or injection in the app cannot add an account. Sessions carry a foreign key to it.
- **Bootstrap closes for good**, recorded in `admin_owner.bootstrapped_at` under a row lock, not inferred from whether a passkey exists. Removing every passkey must not reopen it.
- **Access email is compared exactly.** Cloudflare sends the address the policy matched; folding case or trimming would only widen what is accepted.
- **Recovery key instead of a database reset.** 256 random bits, shown once at bootstrap, stored with Django's password hasher (see below), single use and replaced on use. It is the only way back after `access/revoke-all` or losing every passkey, so it needs Access, counts towards the sign-in cool-down and is refused if the owner cannot be told. A password-style reset link was rejected: it would add a second way in that needs no passkey.
- **Revoking sessions or all access runs at once, and a failed notice does not stop it.** These only take access away, so delaying them or making them depend on the notifier would help an attacker, not the owner. Both need a fresh passkey confirmation so a stolen session cannot lock the owner out. Revoking a single passkey goes through the 24-hour vital action instead, because a stolen session plus confirmation could otherwise remove the owner's other keys quietly.
- **`NOTIFIERS` defaults to `core.notify.LogNotifier`** in Compose and `.env.example`, so a fresh setup does not refuse every vital action. The settings default stays empty: production must name its notifiers.
- **Ruff rules S106 and S107 are off for tests.** They flag the fixed bootstrap token the tests use on purpose.

## Django built-ins

- **Django's SecurityMiddleware and XFrameOptionsMiddleware set HSTS, nosniff, Referrer-Policy, COOP and X-Frame-Options.** `core.headers` now adds only what Django lacks: CSP, CORP, Permissions-Policy and the `no-store` default for Cache-Control. `SECURE_PROXY_SSL_HEADER` trusts `X-Forwarded-Proto`, which Cloud Run sets itself; HSTS is sent on HTTPS requests only, as browsers ignore it over HTTP anyway.
- **Django's CsrfViewMiddleware checks the CSRF token on every state-changing request, including the six sign-in routes.** The secret lives in an HttpOnly `__Host-csrf` cookie (Secure, `SameSite=Strict`, no expiry); the page reads a masked token from `GET /api/v1/admin/csrf` or from the sign-in response and sends it in `X-CSRF-Token`. The secret is replaced on sign-in and on passkey confirmation. The Fetch-Metadata and exact-Origin checks in `core/guard.py` stay on top. `/healthz` is exempt because it is GET only, as the DRF views already are.
- **The recovery key is hashed with `make_password` (PBKDF2) and checked with `check_password`.** It is random enough for SHA-256, but the spec uses Django's hasher for any secret a person keeps, and the cost is one slow hash on a rare route. The column grew to 128 characters. A recovery key stored as plain SHA-256 is no longer accepted; none exists outside development, where bootstrap issues a new one.
- **Sessions stay custom.** Django's session framework would bring `django.contrib.sessions` without giving what 10.5 needs: 256-bit ids stored only as a hash, a 15-minute idle and 8-hour absolute timeout, rotation that keeps the absolute timeout, revoke-all, and a foreign key to the single owner row.
- **Authentication stays custom, and `django.contrib.auth` is not installed.** Sign-in is a passkey behind Cloudflare Access for one owner row. Django's user model would add a password column, users, groups and permissions that nothing uses, and a second way in to defend. Only `django.contrib.auth.hashers` is imported, which needs no models.
- **Session and bootstrap tokens stay hashed with SHA-256.** Both are 256 random bits, so there is nothing to brute-force and a slow hasher adds nothing. Session tokens are looked up on every admin request, which a slow hash would make expensive.

## Phase 2A

- **Items are one table, `section_items`, with a JSON draft validated per section type.** Each section type that holds items (projects, experience, education, skills, gallery, links) has a strict DRF serializer in `core/serializers.py`. One table keeps add, hide, reorder, trash, publish and restore the same code for every type. The typed tables from phase 1 (`projects`, `experience` and so on) were dropped after phase 2B (see below).
- **Serializers refuse unknown fields instead of ignoring them.** This is the mass-assignment guard: a request cannot set ids, positions, visibility, published copies or timestamps by adding keys. Strings must be strings (no numbers turned into text), booleans must be `true` or `false`, and control characters are refused.
- **What is live at once and what waits for Publish.** Section order, show and hide, and moving a section to the trash apply at once, so the owner can take something down quickly. Everything inside a section (title, text, items, their order and visibility) is a draft until the section is published.
- **A version is the whole section.** Publishing stores the section's draft and its live items (with order and visibility) as a numbered revision, and the public copy holds only the shown items. Restoring a version puts it back as the draft; items added since go to the trash rather than being deleted, so nothing is lost. Items deleted for good since cannot come back.
- **Trash: restore for 30 days, then `manage.py purge_trash` deletes.** It is meant to run daily (scheduled in phase 7). Permanent delete before that is the vital action, allowed only for something in the trash and refused if it was restored meanwhile. One-of-a-kind sections (intro, contact) cannot be restored next to a live one.
- **Caps: 40 sections, 200 items per section.** They bound storage and page work. Adding a section or item takes the owner row lock so the caps and the one-of-a-kind rule cannot be raced.
- **Listings are page-numbered, 25 per page.** The audit log keeps its sequence-number paging. Unknown or repeated query parameters are refused, as for the audit log. The admin loads every page of a list it reorders (at most 40 sections, or 8 pages of items).
- **Flagged audit events are a fixed list** (`core.audit.FLAGGED`: failed sign-ins, lock-outs, recovery, passkey changes, revocations, vital actions), not a stored column, so the hash chain is unchanged.
- **Admin at `/desk`.** Not linked from the public site, `noindex` in the page and in `X-Robots-Tag`, and `Cache-Control: no-store`. Cloudflare Access must cover `/desk/*` and `/api/v1/admin/*`. The name is not a secret.
- **The web service passes `/api/v1/*` to the API itself** (`app/api/v1/[...path]/route.ts`), reading `API_URL` at run time, so the admin and the API share one origin and the API's exact-Origin and Fetch-Metadata checks hold. Only the headers the API reads are forwarded. Bodies over 1 MB, dot segments and over-long paths are refused. With no `API_URL`, or no answer, it returns 503.
- **Reorder uses Up and Down buttons, not drag.** They work with a keyboard, a screen reader and on a phone. Drag can be added later on top.
- **Passkey confirmation is a dialog with its own button.** Some browsers only allow a passkey prompt straight after a click, so the admin does not start one by itself after a refused request.
- **Browser tests run the real API** through `api/tests/e2e_server.py`: a fresh `*_e2e` database each run and a throwaway RSA key in place of Cloudflare's key list. The token is still checked in full; nothing in the API's checks changes. The CI web job gets Postgres, Redis and Python for this.
- **No new dependencies.** WebAuthn in the browser is about 100 lines in `web/lib/admin/webauthn.ts` rather than a library.
- **Admin colours are CSS variables in `app/globals.css`,** swapped for the dark theme. Fonts fall back to system faces until the self-hosted fonts arrive with the public design in phase 3.

## Phase 2B: content editors

- **Content stays in `section_items` as JSON, one strict shape per type.** The editors did not need the phase 1 typed tables (`projects`, `project_images`, `project_fields`, `tags`, `experience`, `education`, `skill_groups`, `skills`, `links`). They were unused and are dropped by migration `0006_drop_typed_content`, with their models and grants; `media` stays, because image slots point at it. All content now lives in `section_items`.
- **Section edits are merged, then the whole draft is checked.** A PATCH sends only the fields that changed; the API puts them over the stored draft and validates the result against the section type's shape, so a partial edit cannot skip a required field such as a photo's alt text.
- **Project shape.** Title, short description, case study (Markdown), status (live, demo, local, in progress), created month (may be empty while in progress), category for the filter, card colour from a fixed list (orange, blue, pink, olive, yellow, black), tags (30, each once), links (10, kind demo, code or other, https only), label/value fields (20) and image slots (8). Experience gains tags; education gains a grade.
- **Image slots hold alt text now and a media id later.** The id must name a live row in `media`; until the media library exists it is empty and the admin says so. Alt text is required for every slot.
- **Markdown becomes React elements, never an HTML string.** `web/lib/markdown.ts` parses with markdown-it (CommonMark, HTML off) and builds elements from an allow-list: paragraphs, two heading levels under the section heading, lists, quotes, code, rules, emphasis and links. Raw HTML shows as text, images show as their alt text (pictures come from image slots), links are kept only for `https`, a site path or an anchor. There is no `innerHTML` anywhere, so Trusted Types has nothing to guard here. The public site in phase 3 uses the same function.
- **Two new web dependencies.** `zod` for client validation (SPEC 10.4 names it). `markdown-it` for parsing: widely used, small, and a hand-written parser would be riskier.
- **The privacy check warns; the API enforces the warning.** Email addresses, phone numbers (10 to 13 digits starting with 0 or +) and UK postcodes in anything Publish would put live are listed in the editor. Publish is refused with `409 privacy_check` unless the request says `confirm: true`. Hidden items are not checked because they are not published. False positives are possible; the owner decides.
- **Theme tokens: four colours per mode.** Background, text, accent and text on accent, for light and dark. Pairs checked: text on background 4.5:1, text on accent 4.5:1, accent against background 3:1 (WCAG AA for text and for interface parts). Colours are `#rrggbb` only, stored in lower case, never free CSS. Presets (orange, blue, olive) live in `api/core/theme.py` and are served with the settings, so there is one list. The editor shows ratios as you type and will not save a failing pair; the API refuses it too.
- **Settings are one row, drafted and published like a section,** with a numbered revision per publish. They hold title, description, contact form on or off, showcase layout and visitor switcher, SEO title and description for a fixed set of pages, a social preview image slot and the theme. Social links are not repeated here: they are the Links section.
- **Cache purge on publish** came in phase 2C (below).

## Phase 2C: media library and cache purge

- **One new dependency: Pillow.** It decodes and re-encodes images; nothing else in the standard library can. Google Cloud Storage and Cloudflare are each a few HTTPS calls with `urllib`, so no cloud SDKs.
- **The bytes decide what a file is.** Pillow opens JPEG, PNG and WebP only; the file name and the type the browser declares are ignored. SVG is refused (it can carry script), and so are GIF, BMP, PDF and anything else. Limits: 8 MB per file, 40 megapixels, one file per upload, 50 uploads a day.
- **Every image is drawn again from its pixels as WebP** at 480, 960 and 1600 px wide (never scaled up). Camera rotation is applied first, then EXIF, GPS, XMP, ICC profiles and anything after the image data are left behind. The original is not kept. Alt text (one line, up to 300 characters) is required at upload and on every edit.
- **File names are 128 random bits plus the width** (`<32 hex>-<width>.webp`). Storage refuses any key outside that pattern, and local disk also checks the resolved path stays in the store root.
- **Storage is an interface with save, read and delete.** `MEDIA_STORAGE=local` (development, tests, compose volume) or `gcs` (production: a private bucket, written with the Cloud Run service account's token from the metadata server). R2 can be added as a third class. If storage fails during an upload, the sizes already stored are removed and the API answers 503.
- **Visitors get images through the API, not from the bucket.** `GET /api/v1/media/<name>` serves a size only when the image is used by a published, shown section or the published settings, and is not in the trash; anything else is the same 404. Responses are `immutable` for a year, so after the first request the edge serves them. Unpublished images are visible only in the admin (`/api/v1/admin/media/<id>/file`, session needed, `no-store`).
- **`GET /api/v1/site` is the one public read of content:** published settings, the published copy of each shown section in order, and the image sizes they use. It is the document the public pages in phase 3 render from. `s-maxage` of a year because every change that goes live purges it; `stale-if-error` of a week, so the edge keeps serving the last good copy if the API is down (fail static).
- **Cache purge uses `purge_everything` on the zone** with a token that has only the Cache Purge permission. The site is small, so purging by URL is not worth the bookkeeping. It runs after section or settings publish and after the changes that go live at once (section order, show and hide, trash and restore, image trashed). The change is saved first; a failed purge is kept on the settings row, audited, shown as a banner with a retry button, and cleared by the next purge that works. `CACHE_PURGER=core.purge.LogPurger` (the default) only logs.
- **Request bodies are capped in the API guard too**, before anything reads them: 1 MB, or one image plus its form on `POST /api/v1/admin/media`. The web proxy applies the same two limits. Uploads are held in memory only.
- **Media in the trash cannot be deleted for good early.** The vital-action allow-list stays as it is; trashed images stop being public at once and `purge_trash` removes them and their files after 30 days.
- **Admin request cap raised from 120 to 300 a minute.** Each thumbnail on the media page and in the image picker is an admin request, so 120 was reached in normal use. The cap is per client, behind Cloudflare Access, so 300 still stops a runaway script.
- **Image slots pick from the library.** The editor shows a thumbnail of the chosen image, fills empty alt text from the library, and can change or clear the image. The media page lists 25 images per page.

## Phase 3A-0: static export on Cloudflare Pages

- **The web app is a static export on the Cloudflare Pages free plan; Cloud Run runs the API only.** Pages serves files from the edge with no request limit and no cold start, and the site needs no server: public pages change only on publish, and the admin is a client-side app. Pages Functions, SSR, middleware, route handlers, server actions and `cookies()`/`headers()` are not used, because they run on Workers and count against the free limits. `web/scripts/check-export.ts` fails CI if any appear. This replaces the web Cloud Run service and the `/api/v1` pass-through route of phase 2A.
- **Public pages are built from `GET /api/v1/site`** at build time, from `API_BASE_URL`. If the read fails, the build fails and Pages keeps the last good build (fail static). Without `API_BASE_URL`, or with `SKIP_SITE_FETCH=1` (container images built before their API runs), the site builds without content; on Pages (`CF_PAGES`) that is refused. `API_BASE_URL` is a public address; no secret reaches the build or the bundle, and CI checks the output for the values of secret-named variables.
- **The admin calls the API on its own host with `credentials: 'include'`.** The site and the API are hosts of one domain (for example the site and `api.` under it), so the `__Host-`, `SameSite=Strict` cookies still travel and the browser sends `Sec-Fetch-Site: same-site`. The guard now accepts `same-site` as well as `same-origin`, still only with the exact `SITE_ORIGIN`; admin reads with any other `Origin` are refused. A small CORS middleware (no new dependency) answers preflights for `SITE_ORIGIN` only, under `/api/v1/admin/` only, for the two request headers the admin sends. Cloudflare Access must cover the admin paths on both hosts and pass `OPTIONS` through to the API (set up in phase 7). Passkeys are unchanged: the relying party is still the site's host.
- **The API's `Cross-Origin-Resource-Policy` is now `same-site`,** so pages on the site's host can show the API's images. Other sites still cannot embed them.
- **Section editor at `/desk/sections/edit?id=`.** Section ids are made after the site is built, so `generateStaticParams` cannot list them; one static page reads the id from the query string.
- **Rebuild on publish through the Pages deploy hook.** Everything that calls the cache purge (publish, section order, show and hide, trash and restore, image trashed) then asks for a build. At most one call per two minutes, decided under a lock on the settings row; a change inside the window is kept as pending and goes out with the next change or with "Build the site now" in the admin. Each call and each debounced request is audited. The last call, its result and any pending change show at the top of the admin. `PagesDeployer` accepts only `https://api.cloudflare.com/client/v4/pages/webhooks/deploy_hooks/<id>`, so a wrong value cannot send the request elsewhere; errors are recorded by type only, so the URL is never logged. The hook only queues a build; whether the build passed is shown in the Pages dashboard. The cache purge stays, for `/api/v1/site` and media.
- **CSP by hash, written after each build.** Next.js puts several inline scripts in every page, and a static page cannot carry a per-request nonce. `web/scripts/write-headers.ts` hashes each page's inline scripts and styles and writes `out/_headers`: static headers and the 404 page's policy on `/*`, then each page removes that policy and sets its own. Pages' limits (100 rules, 2000 characters a line) fail the build if reached. `EXTRA_SCRIPT_HASHES` in `web/lib/security-headers.ts` is the place for a hand-written script (phase 3A-4). The file is generated into `out/`, not `public/`, because the hashes are only known after the build. The development server sends no policy.
- **Next.js prefetch files are renamed after the build.** The export writes nested pages' prefetch files as `__next.desk/sections/__PAGE__.txt` while the client asks for `__next.desk.sections.__PAGE__.txt`; on a static host the request never settles. `web/scripts/flatten-segments.ts` renames them, and the export check fails if a nested one is left.
- **`web/scripts/serve-static.ts` serves `out/` as Pages does** (`x.html` for `/x`, `404.html` with status 404, `_headers` rules in order, `!` removing a header). The browser tests build against the real API and run on it, and the web container uses it for Docker Compose and the `kind` demo. The scripts are TypeScript run by Node directly.
- **Fonts by `next/font/google`.** Bricolage Grotesque, Instrument Sans and IBM Plex Mono are downloaded while building and served from `/_next/static/media`; visitors never contact Google. No new dependency. The build needs network access to Google Fonts.
- **Image widths unchanged.** Phase 2C already stores WebP at 480, 960 and 1600 px (never scaled up; a smaller image keeps its own width as the largest size) and lists them in `GET /api/v1/site` and the media API. No migration was needed; `srcset()` in `web/lib/site.ts` builds the attribute with the API origin in front.
- **No health route on the web side.** Static files need none; the API keeps `/healthz`.
- **Terraform and Kubernetes.** None exists yet. When phase 7 writes it, Terraform covers the API Cloud Run service only; the Pages project, its custom domain, build settings and deploy hook are set up by hand in the Cloudflare dashboard. The Kubernetes manifests for `kind` keep both containers as a local demo.
- **Pages limits for `_headers` are checked twice.** The writer refuses more than 100 rules or a line over 2000 characters, and `check-export.ts` measures the written file again. Each page keeps its own rule while the page rules fit in 90; past that, the route pattern with most pages (for example `/projects/*`) is folded first into one rule holding the union of its pages' hashes and the 404 page's. Today: 15 rules, longest line 599.
- **A build fails if `GET /api/v1/site` is unreachable or answers an error,** so Pages keeps the last good build. A build where it answers but nothing is published goes ahead: `/desk` is in the same build, so refusing would stop the owner from ever publishing the first section (SPEC 17: placeholders, never blocking). The home page then shows the site title (or "Portfolio"), "Site coming soon" and a `noindex` meta tag, and no other public page is built. `web/scripts/check-build-refuses.ts` runs real builds against a stub API in CI: down and error must fail, empty must pass with the placeholder and `/desk`. The browser tests' API still publishes one section (`Seeded`).
- **The Next.js fetch cache is cleared before each build.** Next stores build-time fetch answers in `.next/cache/fetch-cache` and Pages restores `.next/cache`, so a build could reuse an old site document and never see an outage or an unpublish. The build check fills the cache with a good answer first, so reuse fails it.
- **CORS allows GET, POST and PATCH only,** the methods admin routes take; PUT and DELETE were dropped. `Vary: Origin` is on every admin response, with or without CORS headers.
- **A browser test fails if any prefetch request gets a 404,** so a Next.js upgrade that changes the prefetch file names is caught in CI.

## Phase 3A-1: palette data model

- **Palettes are rows in a new `palettes` table** (random UUID, name, kind `preset` or `custom`, light and dark slot sets as JSON, timestamps, `trashed_at`). Each mode fills thirteen slots: `bg`, `ink`, `surface`, `primary`, `on_primary`, `accent_1` to `accent_4`, `on_accent_1` to `on_accent_4`. The app role gets read and write on it in `db/grants.sql`.
- **Colours are `#RRGGBB`, stored in upper case.** Anything else is refused, including short hex, named colours, `url()`, `var()` and strings carrying CSS. The 2B rule was lower case; the spec now says upper.
- **Contrast pairs, in light and in dark:** `ink` on `bg` and on `surface`, `on_primary` on `primary`, each `on_accent_n` on `accent_n` at 4.5:1. (The 3:1 rule for `primary` against `bg` was dropped in 3A-2; see there.) Errors sit under the mode and read "Light: ink on bg is 4.48:1; it needs at least 4.5:1." `web/lib/admin/contrast.ts` does the same sums with the same wording.
- **Presets A to E are made by migration `0010_palette_data` with fixed ids,** so new settings can name Original (E) as the default. The dark sets and the slots the spec does not give (surface, on-colours, the accents of A to D) were chosen to pass every pair. Original's light primary was briefly `#E8551C` to pass a 3:1 rule against the cream; 3A-2 put it back to `#FF5A1F`.
- **Presets cannot be edited or deleted** (409 `preset`); duplicate one to customise. At most 12 custom palettes (409 `palette_limit`, checked under the owner row lock, and again on restore). Conflicts now carry a short `code` so the admin can explain them.
- **The choice of palettes is three settings fields:** `palette_mode` (`fixed`, `rotate`, `pick`; default `fixed`), `default_palette_id` and `enabled_palette_ids` (1 to 17, each once, each a live palette, the default among them). `POST /palettes/use` sets them; a settings edit checks the same rules.
- **Palette rows are drafts; settings publish takes a copy.** Publishing the settings stores the enabled palettes' colours with the published settings, so editing a palette changes nothing live until the next publish, and that publish runs the cache purge and the Pages rebuild. "Unpublished changes" compares the draft settings plus the enabled palettes. Palette names are checked for contact details like other published text; palette ids are not scanned, since a run of digits in one can look like a phone number.

Trashed palettes are restored within 30 days or removed by `purge_trash`; like media they are not on the vital-action delete list.
- **`GET /api/v1/site` returns `palettes`:** only the enabled ones, as last published, each with id, name, light and dark. The settings carry the mode, default id and enabled ids. Before the first settings publish the list is empty.
- **The 2B theme moved into palettes and its field is gone.** A theme still equal to the 2B default becomes Original; any other becomes a custom palette (surface = background, accents from Original, so every pair still passes). The live copy is kept as it was. The 2B theme editor in /desk is removed; the palette editor comes in 3A-4.
- **Admin routes:** `palettes` (list, create), `palettes/use`, `palettes/<id>` (get, edit), `palettes/<id>/duplicate`, `palettes/<id>/trash`, `palettes/<id>/restore`. All go through `admin_route(Level.SESSION)`, so the route tests try each with no, expired, revoked and wrong sessions and without the CSRF token. Each change is audited (`palette_added`, `palette_duplicated`, `palette_changed`, `palette_trashed`, `palette_restored`, `palettes_chosen`).

## Phase 3A-4: visitor palettes, light and dark, script hash, cache headers and rate limits

SPEC sections used: 4.2b, 4.5, 4.7, 4.9, 4.10, 7, 10.3, 10.4, 10.12, 11.1, 11.3, 14.

- **The visitor's choice is kept in `localStorage`, never a cookie.** Keys: `palette` (visitor picks), `palette-last` (rotation), `theme` (`light` or `dark`; absent means match the device). A new visit for rotation is an empty `sessionStorage` key `palette-visit`. A cookie would go to Pages on every request for no purpose and would need a notice; the values are palette ids and a theme name, not personal data. Every read and write is in try/catch; with storage off, the page uses the default palette and the device theme.
- **One inline boot script in `<head>`** (`web/lib/public/boot-script.ts`) sets `data-palette` and `data-theme` on `<html>` before the body is parsed. It reads the owner's choice from attributes the build writes on `<html>` (`data-palette` default, `data-palette-mode`, `data-palettes` enabled ids), so its text is the same on every build and every page. Its SHA-256 is in `EXTRA_SCRIPT_HASHES`; a unit test recomputes it from the text and fails on drift. The build also hashes every inline script it finds, so the page policy lists it either way. No `'unsafe-inline'`.
- **Modes.** Fixed: the default only, a remembered pick is ignored. Rotate: the first visit gets the default, each new visit the next enabled palette in the published order; one palette for the whole visit; no picker. Visitor picks: the remembered palette if still enabled, otherwise the default, with no error.
- **Theme has three states,** device (default), light and dark, on `data-theme`. Palette CSS gives dark values under `@media (prefers-color-scheme: dark)` unless `data-theme="light"`, and always under `data-theme="dark"`. Without JavaScript there is no attribute and the device decides. `color-scheme` follows, so scrollbars and controls match.
- **The menu is one "Theme" disclosure in the nav,** prerendered `hidden` and shown by `DisplayEnhancer`, because nothing can apply a choice without JavaScript. Native radio groups in fieldsets with legends (arrow keys work), 44 px rows, Escape closes and returns focus, a polite live line names the new choice. The palette group is built only in "visitor picks" mode with two or more palettes, and the enhancer removes it if the page says another mode. Swatches are `data-palette` spans, so they take each palette's own tokens with no `style` attribute.
- **`GET /api/v1/site`: `public, max-age=60, s-maxage=120, stale-while-revalidate=60, stale-if-error=604800`,** with a strong ETag (SHA-256 of the body) and 304 on a match. Publish purges the edge; if the purge fails, the edge copy is at most two minutes old, the same as the rebuild debounce in SPEC 7. The edge still answers nearly every read, so the database sees about one read per two minutes per edge location. Images keep `immutable` (random names).
- **Public pages: `public, max-age=0, must-revalidate`** in `_headers` (Pages sends the ETag), so the next page load after a rebuild shows the new palettes. `/_next/static/*` stays `immutable` and `/desk` stays `no-store`; both remove the page value first so no response has two `Cache-Control` headers. The API's admin routes stay `no-store` (default in the headers middleware).
- **Public read cap: 120 requests per minute per client** for `/api/v1/site` and public images together (`PUBLIC_REQUESTS_PER_MINUTE`), 429 with `Retry-After`. The SPEC sets no number; this is far above what a build or a visitor needs once the edge caches. Public reads fail static: with Redis down or unset the cap is skipped and logged, and the read is served. The client is `Cf-Connecting-Ip`, which is only trustworthy once the origin lock rejects traffic that did not come through Cloudflare; until then the edge rate limit is the real layer.
- **Browser tests publish "visitor picks" with presets A, B and E;** the draft stays at the defaults the admin tests expect. The fixed-mode test serves the built home page with `data-palette-mode="fixed"`, which is exactly what a fixed build differs by; the markup rule (no picker unless picks) has its own unit test.

## Phase 3B: section transitions, showcase layouts, project pages and the skills strip

- **`client_key` reads `Cf-Connecting-Ip` only if it parses as an IP address** (`ipaddress.ip_address`); a missing or malformed value falls back to `REMOTE_ADDR`, so a client cannot pick a fresh rate-limit key per request by sending any string. ## Phase 4A: contact form, bot defences and admin inbox

- **Routes are `/api/v1/contact` and `/api/v1/contact/start`,** under the versioned prefix like every other route (the brief wrote `/api/contact`).
- **New tables `contact_messages` and `contact_notes` (migration 0013); migration 0014 adds `reason`, `spam_score` and the retention periods; migration 0015 drops the old, unused `messages` table.** Its vital-action allow-list entry now points at `ContactMessage`, and the tests that used it were moved over. Each migration reverses (tested).
- **Bot check is Cloudflare Turnstile, verified on the server (SPEC 3.8, 10.13).** The brief first asked for a proof-of-work challenge; the owner corrected it: where the brief and the SPEC differ, the SPEC wins. The page sends the token the Turnstile widget produced as `turnstile`; `core/turnstile.py` posts it with the secret key to Cloudflare's `siteverify` (5 s timeout, nothing else sent: not the visitor's address, not the message). A token Cloudflare refuses (invalid, missing, expired, already used) gets the 400 `challenge` answer. If Cloudflare cannot be asked or its answer cannot be trusted (network error, timeout, not JSON, `success` not a boolean, or an error code that is our fault such as a bad secret), the answer is 503 and nothing is stored: fail closed. **No secret key set also means 503,** so a deployment that forgot the key never runs without the check. The check is pluggable (`TURNSTILE_VERIFIER`, as the purger and deployer are) so tests never call Cloudflare.
- **Dummy keys for development and tests.** Cloudflare publishes test keys: secret `1x0000000000000000000000000000000AA` always passes (`2x...` always fails, `3x...` reports a spent token); the matching site keys are `1x00000000000000000000AA`, `2x00000000000000000000AB` and `3x00000000000000000000FF`, and the dummy widget gives the token `XXXX.DUMMY.TOKEN.XXXX`. `tests/settings.py`, `docker-compose.yml` and the e2e API use the dummy secret (the tests and e2e swap the network call for a local stand-in with the same rules, so they need no network); `.env.example` lists the name only and production sets a real secret. Removed with this change: the `/contact/challenge` route, proof-of-work, its Redis single-use keys and the difficulty and expiry settings.
- **Turnstile and the CSP.** The widget loads its script and frame from `challenges.cloudflare.com`, so the public form page's `script-src` and `frame-src` need that origin, and `connect-src` needs the API (below). The brief forbids CSP loosening, so this is part of the open decision at the end of this section, and Part 4 is not built.

- **The form-start token** is a signed value (`unix-seconds.signature`, HMAC-SHA256 over the secret key with a purpose label) from `GET /contact/start`, fetched when the form is opened (own bucket: 30 an hour per address). It lets the server see that a form was open for at least 3 seconds without storing anything. A missing, forged, future-dated or over six-hours-old token gets the same bad-check error as a refused Turnstile token, and Cloudflare is not asked about it. A person who leaves the form open longer is asked to try again, and the client keeps what they typed.

- **Check order:** shape and validation first (field errors, no state touched); then the address limit; then the form token and Turnstile; then the email limit and the daily cap; then the bot checks; then store. So someone without a good token cannot use up another person's email allowance, and a flood of bad posts is stopped by the address limit before Cloudflare is asked.

- **Quarantine and the spam score (SPEC 5.8a (d)).** Each message gets a score from 0 to 100 and is quarantined (status `spam`, same 201 answer as a real message) at 100. A filled honeypot (`website`), a submission under 3 seconds, more than two links (`http://`, `https://`, `www.`) or a body already seen in the last 24 hours each score the full 100. Below that, each link adds 20 and each advertising word from a short fixed list adds 25 (at most 75), so two links and three such words together quarantine a message, while one link or one word alone does not. The score is stored and shown to the owner in the list and on the message. The list of words is in `core/contact.py`; it is deliberately short and the owner can review every quarantined message and move it back with "Not spam". A real message sent twice in a day is quarantined the second time.
- **Rate limits have their own Redis buckets (`contact:*`),** apart from the 120 a minute public bucket that images share: 5 messages an hour per address, 3 a day per email (case-insensitive, keyed hash), 25 a day in all (SPEC 11.2), and 30 form starts an hour per address. Windows are fixed (UTC hour, UTC day). Quarantined messages and refused attempts count, so a bot cannot use the quarantine to get past the limits. Redis or the database down gives 503 and stores nothing (fail closed).
- **Addresses are hashed,** `HMAC-SHA256(secret key, "contact-address:" + address)`, stored in `ip_hash`. The raw address is never stored or logged. Changing the secret key changes the hashes; with 90-day retention that only affects the link between old messages. The address is `Cf-Connecting-Ip` as `ratelimit.client_address` reads it; it is trusted fully only after the Phase 7 origin lock (see PROGRESS).
- **Retention follows SPEC 5.8a (the owner's brief said 90 days; the SPEC wins).** Spam is kept 30 days, other messages 12 months (365 days), and a message the owner marked kept, or has written notes on, is never removed by the daily job. Both periods are stored on the settings row (`retention_spam_days`, `retention_message_days`), edited under Settings, "Message retention" (7 to 3650 days, whole numbers; reading needs a session, saving a passkey confirmed in the last few minutes, since a short period would remove messages for good), outside the draft and published copies so they never reach the public site (tested). `expires_at` is set when a message arrives, moved when it changes between spam and not spam, and every message's is moved when a period is saved (`core/retention.py`), in one transaction with the audit entry. The daily job that acts on `expires_at`, kept and notes is 4B. A public message never creates the settings row; it reads the defaults (30 and 365) until the owner saves.

Name 1 to 100 characters, email up to 254 with Django's validator plus no spaces, quotes, angle brackets, commas or semicolons, message 10 to 4000, and an optional reason that is exactly `hiring`, `project` or `other` (SPEC 3.8; blank is stored as none). New lines are rejected in name and email, and every control, bidi-override and zero-width character is removed from all three. All kinds of line ending in the message become one plain line break; tabs become spaces. Stored as plain text; the pages show it as text, never HTML.
- **Logs** carry `id=<uuid> outcome=<code>` only (`stored`, `spam_honeypot`, `spam_timing`, `spam_links`, `spam_repeat`, `bad_challenge`, `rate_limited`, `invalid`). Public submissions are not written to the audit log, so a flood cannot fill the hash chain; the inbox actions are (Part 2).

- **Inbox API** (`core/inbox.py`, `core/inbox_views.py`), all at level `SESSION` through `admin_route`, so the existing permission, CSRF, throttle and origin checks apply and `test_routes` and `test_csrf` cover the new URLs automatically. "Delete for good" asks, then requests a `permanent_delete` of `{entity: message, id}`: a fresh passkey, a 24-hour wait, a 7-day window, a notice to the owner, and a cancel that needs only a session. The audit entries (`vital_action_requested`, `vital_action_executed`) hold the action id, kind and the target `{entity, id}` only; a test reads the whole audit table for the message's name, email, text and notes and finds none.

## Phase 4B-1: retention job, spam clock, editable limits

- **The spam retention clock starts when a message becomes spam** (owner decision). New column `spam_at` (migration 0016, backfilled from `created_at` for spam already stored; reverses). It is set to the arrival time when a message arrives as spam, to now when the owner marks one spam, and cleared by "Not spam", which restores the 12-month rule from arrival. Spam's `expires_at` is `spam_at` plus the spam period, so an old message marked spam today has the full 30 days. Saving the periods moves every spam message's expiry from its `spam_at` (falling back to `created_at`).
- **Two daily caps** (owner decision; supersedes "Quarantined messages count" for the daily cap in Phase 4A). The cap of 25 a day counts only messages that are not spam. Stored spam has its own cap, 20 a day (the checklist had 100; the owner's 4B-1 brief set 20). Past the spam cap, the answer is still "received" (a bot must not learn it was caught) but the message is not stored; the log line is `contact outcome=spam_dropped` with no id. The per-email (3 a day) and per-address (5 an hour) limits are unchanged and count every attempt, including dropped spam.
- **Check order is now:** shape and validation; address limit; Turnstile; email limit; body marker and spam score; then the cap for the message's kind; then store. Any refusal after the body marker is taken (a cap, a dropped spam, a failed store) gives the marker back, unless the body was already a repeat, whose marker belongs to the message stored before.
- **`manage.py run_retention`** (`core/retention.py`), meant to run daily (scheduled in Phase 7). Each batch is one DELETE statement whose WHERE holds every rule: `expires_at` passed, not kept, no notes. The rules are a tuple (`retention.rules`); Phase 4B-3 adds "not linked to a contact" as one more entry once the contacts table exists. One statement means no gap between choosing rows and deleting them; `QuerySet.delete()` would select first to look for notes to cascade, so the job uses the ORM's single-statement delete. The batch is chosen by an inner select with `FOR UPDATE SKIP LOCKED`, so a message another transaction holds (adding a note locks the message first) is skipped, not waited on, and the outer WHERE checks every rule again on the row as it stands. The batch is matched with `id = ANY(ARRAY(subquery))`, not `IN`: with statistics from an empty table Postgres chose a plan that ran the `IN` subquery again per deleted row and removed 4 rows from a batch of 3 (regression test). The notes foreign key is a last guard: were the notes rule ever missing, the delete would be refused and the run undone (tested).
- **The job runs in one transaction under a Postgres advisory lock** (`pg_try_advisory_xact_lock`, fixed key). A second run while one holds the lock does nothing and exits non-zero; a database error also exits non-zero and deletes nothing. Options `--dry-run` (counts only, deletes nothing) and `--batch-size` (1 to 10,000, default 500). One audit entry per run, `retention_run`, with `deleted`, `exempt` (past their date but kept by a rule, or held by another transaction), `batches` and `dry_run` only: never ids, names, addresses or text. The app database role can run it and still cannot change the audit log (tested); no grant was added.
- **No hand-written SQL in the job.** `tests/test_injection.py` refuses `.execute(` and the like in application code, so the lock is asked through the ORM (a function call over the one owner row) and the delete is built by the ORM.
- **Editable contact limits** (migration 0017, `core/limits.py`): daily cap for messages that are not spam (default 25, 1 to 200), spam daily cap (20, 0 to 200), per address an hour (5, 1 to 50), per email a day (3, 1 to 20), minimum seconds open (3, 0 to 30), most links (2, 0 to 10) and spam threshold (100, 50 to 100). Stored on the settings row apart from the draft and published copies, like the retention periods, so they never reach the public site (tested). A field left empty (null) means the default in `settings.py` (`CONTACT_*`), so a deployment can change a default without a migration and a message never creates the settings row. The form reads the values in force once per submission. One module holds the bounds; the serializer is built from it (tested that they agree).
- **`/api/v1/admin/limits`:** GET needs a session; PATCH needs a passkey confirmed in the last few minutes (`elevate=("PATCH",)`, as for retention). Any subset of the fields, at least one, whole numbers only, unknown names refused. One audit entry per change, `limits_changed`, listing each changed field's old and new numbers; saving the same values writes none. GET also lists the fixed limits (public and admin requests a minute, sign-in failures per client and overall, the failure window and lockout, session idle and absolute timeouts, how long a passkey confirmation lasts and the vital-action wait), read from the settings and module constants that enforce them at the time of the request, so the list cannot drift.
- **Departure from SPEC 10.7: changing a limit needs a fresh passkey confirmation, not the 24-hour vital-action wait.** SPEC 10.7 lists "change security settings" as a vital action. These limits tune the form's flood control and every value is bounded, so the worst a stolen session can do is set them to the loosest bound or the strictest; a passkey confirmation stops a stolen cookie alone from doing that, and the audit entry shows it. A day's wait would make an attack in progress harder to answer (raising a cap during a genuine spike, or lowering one during a flood). Reconsider if a limit is added that weakens authentication.

## Phase 4B-2: blocklist and delete everything about an email

- **The blocklist stores only the keyed hash of an email** (`contact.email_hash`, the HMAC the per-email limit already uses: trimmed, lower case, keyed with `SECRET_KEY`). Table `blocked_senders` (migration 0018): hash (unique), an optional owner note of up to 200 characters, created and expiry dates. The app role may insert, read and delete rows but may update only `expires_at` and `note`, so a stored hash is never rewritten (tested). Neither the list, the routes' answers, the logs nor the audit entries show the address or the hash (tested). Rotating `SECRET_KEY` would make every entry stop matching; that is accepted, the same as for the per-email limit.
- **A blocked sender is answered exactly like dropped spam:** the same 201 "received" body, nothing stored, log line `contact outcome=blocked_dropped` with no id. The check runs after Turnstile and before the per-email limit, the body marker and both daily caps, so a blocked sender uses none of them (tested on the Redis keys). The per-address limit still counts the attempt, as it runs before Turnstile. Case and surrounding spaces do not get past a block; any other difference in the address does (tested).
- **Routes:** `GET /admin/blocklist` (session) lists entries, the number that still block and the cap; `POST /admin/blocklist` with `email` and optional `note`, `POST /admin/blocklist/<id>/remove`, `POST /admin/blocklist/<id>/renew` and `POST /admin/messages/<id>/block` need a passkey confirmed in the last few minutes. POST rather than DELETE, as every other admin change is. Blocking an address already blocked keeps its one entry. Blocking from a message moves it to spam and sets `spam_at`; a message already in spam keeps its spam clock.
- **The list holds at most 500 entries that still block** (`blocklist.MAX_ENTRIES`, listed with the fixed limits). Expired entries do not count, and renewing one that still blocks is always allowed; adding past the cap answers 409 `blocklist_full`. Adds are serialised on the settings row lock so two cannot both pass the check.
- **Entries expire after 12 months by default** (calendar months; 31 January plus one month is the last day of February). The lifetime is an editable limit, `blocklist_months`, 1 to 36, audited with old and new numbers like the other limits. A change applies to entries added or renewed after it; existing entries keep their date (simplest, and the owner can renew). Renewing sets a full new lifetime from today. Expired entries stop blocking at once and the daily `run_retention` job removes them in the same transaction as the messages; its audit entry and output gain `blocklist_deleted`.
- **Delete everything about this email** is a vital action, kind `erase_sender`, requested from a message with `also_block` true or false (both fields required). Contact messages now carry `email_hash` (migration 0019, filled for messages already stored; set on every save) so all of a sender's messages can be found without the address. The pending action stores the hash, the choice and the counts at the time it was asked; the admin is shown the counts and the choice, not the hash. The audit entries hold the same, plus the counts deleted; no address, name, body, note or message id (tested on the stored JSON).
- **When it runs** it finds the messages again by hash, so messages that arrived during the wait go too, and so do kept messages and messages with notes (the owner asked for it). It takes the retention job's advisory lock (if the job is running the action answers 409 and stays pending), locks the sender's messages so no note can be added meanwhile, then removes notes and messages in batches of single DELETE statements, inside one savepoint: a failure part way leaves every row in place and the action pending (tested). Without "also block" the sender's blocklist entry is removed; with it, an entry that blocks is kept as it is, or one is added with the normal lifetime. If that would pass the cap, nothing is removed and the action answers 409.

## Phase 4B-3a: contacts and blocklist changes (API)

- **Contacts are separate from messages** (SPEC 5.8a (c), owner decision). Table `contacts` (migration 0020): name, email, the keyed email hash (unique, so one contact per email), organisation, up to 10 tags of up to 30 characters, notes up to 5000 characters, an optional follow-up date (2000 to 2099). A contact is made only from a message, which copies the name and email and links that message; the email is never edited afterwards, so the hash always matches it. Only messages from the same email can be linked (409 `different_sender` otherwise), so delete-everything about that email always covers every linked message. A second contact for the same email answers 409 `contact_exists` (the unique index decides, so two requests at once cannot both pass).
- **Deleting a contact never deletes a message.** `contact_messages.contact_id` is set to null when its contact goes (`SET_NULL`), and deleting a message leaves the contact. A message linked to a contact is never removed by the daily job: `retention.rules` gains `contact_id IS NULL`, inside the same single DELETE statement as the other rules. Unlinking makes the message due again on its existing date.
- **Routes under `/api/v1/admin/contacts`:** list (25 a page; search by name, organisation or email; `tag`; `due=1` for a follow-up date today or earlier, UTC), detail with notes and linked messages, create from a message, PATCH, link and unlink need a session; delete (`POST .../delete`, as other admin changes are POSTs) needs a passkey confirmed in the last few minutes. No answer includes the email hash. Audit entries hold the event, the contact id and, for an edit, the names of changed fields; never a name, email, tag or text. An edit that changes nothing writes no entry. The app role may select, insert, update and delete contacts; `db/grants.sql` lists the table.
- **Delete everything about an email covers contacts** and can be started from a message or a contact (exactly one of `message` or `contact`, plus `also_block`). The stored counts and the audit result gain `contacts`. When it runs it removes notes, then messages, then the contact with that hash, in the same transaction and under the same lock, so a failure at any step, including the contact, leaves everything in place. Migration 0020 runs queued foreign-key checks before it alters `contact_messages`, as Postgres refuses to alter a table with checks still pending in the same transaction (seen in the migration tests).
- **Visible address per block** (owner decision; default hash only). `POST /blocklist` and `POST /messages/<id>/block` accept `keep_address` (true or false). Only when true is the address stored in `blocked_senders.email` (migration 0021). Privacy effect: a kept address is shown only to the signed-in owner, only while the entry still blocks (an expired entry shows null at once, and the daily job removes the row), and is dropped when delete-everything runs with "also block": the entry is made again under the same id with the hash only, keeping its dates and hit counts, in the same transaction. Without "also block" the entry goes, as before. The app role may update only `expires_at`, `note`, `hit_count` and `last_hit_at`, so a stored address or hash is never rewritten (tested); dropping an address is a delete and insert. Blocking a sender whose entry still blocks leaves it as it is, address choice included (to change it the owner removes and adds again). An expired entry blocked again is made again under the same id with the new choice.
- **Hit counter.** Each entry counts how many messages it stopped (`hit_count`) and when it last did (`last_hit_at`). The form finds the entry and counts the hit in one UPDATE statement, so there is no second lookup and no gap. Counting holds no personal data and never changes what the form answers. If that statement fails, the form answers 503 like any other database failure and stores nothing: it cannot tell whether the sender is blocked, and answering "received" would silently lose a real message. A refused Turnstile check counts nothing, as the block is checked after it.
- **Block notes may not contain "@"** (400 on both routes). It is a guard against pasting an address into the note, not a guarantee: a note can still describe a person in other words, and the owner is the only writer.

## Phase 4C-1: CV delivery API

These replace SPEC 3.7 and 5.9 where they differ (owner decisions).

- **PDF only, public CV only.** Only the public CV (professional details only, SPEC 9.2) is stored. There is no full-CV storage, no one-use link, no Word or HTML CV and no conversion on the site. A fuller version is something the owner attaches to his own email by hand.
- **Visitors view, or download after asking.** There is no download route and no lasting public file URL. After Turnstile and the limits, `POST /api/v1/cv/link` returns a path that works for 60 seconds; the site (a later web phase) fetches it and shows the PDF in a browser viewer inside a dialog. The file is sent `inline`, `no-store`, `noindex`, `nosniff`, with a clean file name from the published site title (letters, digits and hyphens, else `cv.pdf`). Framing stays refused for everyone (`X-Frame-Options: DENY`, `frame-ancestors 'none'`), which is stricter than "no framing by other sites": the viewer reads the bytes with a fetch, so no frame of the API is needed. If the web phase frames the browser's own viewer instead, this header and the API's `default-src 'none'` must be revisited for that route.
- **CORS for the CV routes**: the site origin exactly, never credentials. `/cv/link` and `/cv/request` follow the contact form's rule (POST, Content-Type only, short preflight cache, `Retry-After` exposed). `GET /cv` and `GET /cv/file/<token>` are plain GETs and need no preflight; their answers carry `Access-Control-Allow-Origin` for the site only, with `Vary: Origin`.
- **The link names no id.** It is a Django `TimestampSigner` value with a salt for its purpose (`core.cv.view-link` or `core.cv.download-link`), carrying a keyed hash of the live version's id, not the id. The file route tries each purpose's salt, so a view link never works as a download link or the other way round, then checks the age (60 s), that the purpose's switches are still on (403 if not) and that the hash matches the version that is live now. A view link is sent `inline`, a download link `attachment`; headers, logging and the 404 are the same for both. A bad, changed, expired, other-purpose or outdated link gets the same 404 with no detail. A link is not single use within its minute (each fetch is logged); it is short-lived and the limits sit on getting links (KISS).
- **Limits for view links** (settings): 10 per client an hour (`CV_VIEW_PER_ADDRESS_PER_HOUR`), counted before the Turnstile check so a bot cannot hammer it; 200 a day for the whole site (`CV_VIEW_DAILY_CAP`), counted only for visitors who passed the check, so failures cannot use it up. Over either: 429 with `Retry-After`. Redis or the database down: 503, no link. The file route also counts against the public read cap (skipped if Redis is down, as for images; the link has already passed the limits).
- **The view log is written before the file is sent.** The file is read from storage, then the row is written, and only then is the response sent. If the row cannot be written: 503 and no file, so nothing is served unlogged. If storage fails: 503 and no row. A row holds the time, the version id, the kind (`view` or `download`, migration 0023, default `view`), the Cloudflare country header when it is two capital letters (`XX` and `T1` stored as empty) and the user agent with hidden characters removed, cut to 200 characters. No address, no email, no free text.
- **A copy is had by asking.** `POST /api/v1/cv/request` (name optional, email, an optional note of up to 500 characters, Turnstile, honeypot, timing) runs the contact form's own pipeline (`contact_views.accept`): validation and one-line checks for name and email (header injection), hidden-character removal, the blocklist (a blocked sender gets the same "received" answer and nothing is stored), spam scoring and quarantine, the keyed email and address hashes, retention, contact linking and delete-everything all apply unchanged. The stored body is fixed text ("Request for a copy of the CV.") plus the note. The site sends no email; an email provider comes later.
- **Requests share the contact form's limits** (per address an hour, per email a day, the daily inbox cap and the spam cap, all editable on the limits card). Everything that lands in the inbox counts against one budget, and a visitor cannot double the allowance by using both forms. The repeat check for a request uses the email plus the note, not the body alone, so two people asking without a note are not taken for a repeat; the same person asking twice in a day is quarantined like a repeated message.
- **Message kind.** `contact_messages.kind` (migration 0022), `message` or `cv_request`, default and database default `message`, so existing rows and the contact form are unchanged. The inbox list and detail show it, and the list takes `kind=message|cv_request`. Reply by email works unchanged. Chosen over a separate table so retention, delete-everything, contacts, notes and the blocklist need no change.
- **Three switches: view, request and instant download**, on site settings (default on, database default on; `cv_instant_download_enabled` added in migration 0023, no grant change since the app already updates `site_settings`). Instant download only applies while request is on. Each change, on or off, is a vital action of one kind, `cv_switches`, payload exactly `{view, request, instant_download}`, all booleans; a missing or extra key is refused (fresh passkey, 24-hour wait, notice, cancel, audit `cv_switches_changed` with all three). `GET /api/v1/admin/cv/switches` shows all three and any pending change. View off or no live version: `/cv/link` answers a plain 403, and a view link at `/cv/file` too. Request off: `/cv/request` answers 403. Request or instant download off: a download link at `/cv/file` answers 403. `GET /api/v1/cv` gives `can_view`, `can_request`, `instant_download: true` only when instant download is on, request is on and a version is live, and the live version's date, cached for a minute (and stale for a day if the API fails).
- **Instant download: a link for everyone who passes.** With instant download on, request on and a live version, the success answer of `/cv/request` adds `url` and `expires_in` (60), a download link signed as above. It is given whenever Turnstile and the contact limits pass: to a stored request, a spam-flagged one (stored in spam as usual), one dropped past the spam cap and one from a blocked sender (nothing stored, the blocklist hit counted). The answer has the same shape in every case. Why: the shared "received" answer exists so a sender cannot tell they are blocked or quarantined, and leaving the link out for them would undo that. The CV is public and holds professional details only, so a blocked or spammy sender gains nothing they could not get from the viewer. No link on a Turnstile failure (400), a limit (429), instant download off, no live version, or Turnstile, Redis or the database down (503). Download links count against the contact limits, not the view-link limits, because the request has already spent from that budget.
- **Versions** (`cv_versions`): at most 10 (409 `cv_versions_full` with a message), one live at a time (a partial unique index), never live on upload; setting an older one live is the rollback. Upload and set live need a fresh passkey; listing and the owner's download (attachment, same headers) need a session. Upload checks, all before anything is stored: 5 MB (`CV_MAX_BYTES`, with its own body limit in the guard), not empty, `%PDF-` at the start, `%%EOF` and `startxref` in the last 1 KB, the declared type `application/pdf` and a `.pdf` name, no `/Encrypt`, and none of the names `/JavaScript`, `/JS`, `/OpenAction`, `/AA`, `/Launch`, `/EmbeddedFile` (hex-escaped names decoded; stream bodies skipped to avoid false matches in binary data). This is a heuristic, not a guarantee (a name inside a compressed object stream is not seen); it is enough because the only uploader is the owner behind a passkey. Uploads count against the media daily upload cap.
- **Deleting a version** uses the existing `permanent_delete` vital action with entity `cv_version`. The live version cannot be asked for, and a version made live during the wait is kept (409). The row goes in the action's transaction and the file after it commits; a failed file removal is logged and leaves an unreachable file.
- **Storage.** Keys `cv/<128-bit hex>.pdf`, a pattern of their own that the media store refuses (and the other way round). Development: `CV_ROOT`, a `.cv` folder beside the media root (git-ignored; a `/cv` volume in docker-compose). Production: `GCS_CV_BUCKET`, a bucket of its own; empty refuses with `NotConfigured`. Terraform is not changed: Phase 7 creates and wires the bucket.
- **Grants.** `cv_versions`: select, insert, delete, and update of `is_live` only. `cv_views`: select, insert, delete (the daily job). `cv_day_counts`: select, insert, and update of `count` only. The unused `cv_files` table is dropped. The view log keeps the version as a plain id, not a foreign key, because a set-null foreign key would need UPDATE on the log.
- **Retention** (SPEC 5.8a (e): download logs keep a coarse summary after 90 days; 6.2 does not conflict). The daily job counts views older than 90 whole UTC days into `cv_day_counts` (one grouped count, then each day added to its total through the ORM) and removes them in one DELETE, under the same advisory lock and in the same transaction; the audit entry gains `cv_views_deleted`. `GET /api/v1/admin/cv/views` (25 a page, newest first) and `/cv/views/days` (kept totals plus recent rows) need a session.
- **No PDF library is installed**, so the document's Title and Author are not shown to the owner. pypdf (BSD-3-Clause, free) could do it if wanted later.
- **Audit events** `cv_uploaded` (version, size), `cv_live_changed` (version), `cv_version_deleted` (version), `cv_switches_changed` (view, request, instant_download). No personal data.


## Phase 4C-2: the CV on the site (web)

The API is unchanged. These are the web choices; the rules they follow are in Phase 4C-1.

- **Where it sits.** The CV block closes the home page, after the last section and outside `.section--contact`, so the contact form's own layout and tests are untouched. It is empty markup (`data-cv-block`) until the browser has asked `GET /api/v1/cv` what is on. A switch therefore changes the site within the status's minute, with no build. With both `can_view` and `can_request` false, or if the status cannot be read, nothing is drawn and no word about a CV is on the page. Without JavaScript nothing is shown either (no `<noscript>` note, because the page cannot know whether a CV is on). A build without the API address or a Turnstile key has no block. The old "not available yet" wording in the privacy notice is replaced by a description of what the CV keeps, and the accessibility and security pages each gained a sentence.
- **Lazy loading.** The home page's first load carries only `CvLoader` (a few hundred bytes, the same watch-for-the-viewport idea as the contact form). The block's code, then Turnstile, are fetched when the block is within a screen of the page; the viewer and pdf.js only after a visitor has passed the human check. Home initial JS went from 148.2 to 148.3 kB of 150.
- **Viewer.** A native modal `<dialog>` (as the project sheet), opened after the human check has passed: Turnstile, then `POST /cv/link`, then a `fetch` of the link with credentials omitted, no referrer and no cache, then the bytes go to pdf.js, which draws each page on a canvas. There is no download button, no file address in the page, and no frame, object or embed (the API refuses framing). The link is held in a variable for its minute, never logged, stored or put in an address, and the file is never navigated to. A bad link, an expired link or a failure shows a plain alert with Try again, which gets a new Turnstile token and a new link. The dialog moves focus in, traps Tab (the browser's inert background plus a handler that wraps the first and last control), closes on Escape or Close or a click on the backdrop, and puts focus back on the View button itself, not on whatever had focus, because Safari does not focus a button when it is clicked. It uses no animation of its own; the project sheet's fade runs only without `prefers-reduced-motion`. At 320 px it fits the width and the pages scroll inside it.
- **Accessibility of an image.** Each page is a canvas with `role="img"` and a label ("CV, page 1 of 2, shown as an image"). The dialog says "The CV is shown as page images. For an accessible copy, request one.", and "request one" closes the dialog and moves focus to the request form. If requests are off there is no form, so the sentence is left out rather than point nowhere. The progress and the outcome are read out through a polite live region, and a failure is an `alert`. Reading text out of the PDF (a text layer) was not added: it would make copying easy and is not what a screen reader user needs when a real copy is on offer.
- **pdf.js.** `pdfjs-dist` 6.5.438, Apache-2.0, a free dependency with no service behind it. It is imported with `await import("pdfjs-dist")` inside a function, and the worker is `new URL("pdfjs-dist/build/pdf.worker.min.mjs", import.meta.url)`, so the build emits it as one of the site's own files under `/_next/static/media`: no CDN, no external request. The options turn off everything the page's policy forbids: no `eval` (`isEvalSupported: false`), no scripting or XFA, no fonts made from data (`disableFontFace: true`, so glyphs are drawn from their outlines, which `font-src 'self'` allows), and no WebAssembly (`useWasm: false`, so a PDF that needs the JPEG 2000 or JBIG2 codec shows without that image). Fonts not embedded in the PDF fall back to the visitor's own fonts. Size: the library chunk is about 470 kB (140 kB gzipped) and the worker about 1.27 MB (380 kB gzipped); both are fetched only when a visitor opens the viewer. The static file server for tests gained the `.mjs` type, which a module worker needs; Cloudflare Pages already serves it.
- **Policy.** The home page's policy already allows Turnstile and the API for the contact form. It now does so when the page holds either the form or the CV block (`data-cv-block`), and for no other page. The worker needs nothing more (`worker-src` falls back to `script-src 'self'`).
- **Request form.** Fields are labelled "Your name", "Your email" and "Note" so they never match the contact form's "Name", "Email" and "Message" on the same page. The contact form's pattern is followed otherwise: no field has a name, `method="post"`, a trap field, the timing sent as `elapsed`, one check token per send. One Turnstile widget serves both the view button and the form. After a successful answer (200 or 201) the visitor sees the contact form's own received text. Nothing in the answer is read except the status and a link of exactly the documented shape (`/api/v1/cv/file/<token>` and `expires_in` 60, made absolute from the API's address); any other `url` is ignored. A link adds a "Download the CV" anchor and the note that it works for a minute, and the anchor is replaced by "The download link has expired." once the minute is up. A failure (403, 429, 503, anything else) is said in the site's own words, never the API's text, and keeps what was typed. The `instant_download` flag only adds a line before the fields telling the visitor a link will follow; the button depends on the answer alone.
- **Admin page** `/desk/cv`, in the navigation after Blocklist. *Switches*: three real checkboxes (`role="switch"`) show what is in force; changing any and pressing "Ask to change the switches" asks for the passkey and files one `cv_switches` action with all three values. While a change waits, the switches are locked and the waiting action is shown with its 24-hour wait, a Cancel and (when ready) Run now, through the same `PendingRow` as the Pending actions page. *Versions*: upload (type and size hints; the API's own messages for a wrong, empty, password-protected, scripted or too large file, and for a full list, are shown by the file field; a quick check before sending stops a wrong extension or an oversize file); Set live (passkey); "Download to attach" is a plain link to the API's attachment route; Delete asks for the passkey and files the existing `permanent_delete` action, shown on the row with a cancel; the live version offers no Delete and says why. *Views*: the visit counts by day and the log, 25 to a page, with kind, country and browser. `PendingRow` now words `cv_switches` and CV version deletions.
- **Counts per kind.** The API's day counts have no kind (the kept totals are one number a day), so the page shows visits per day, not per kind. The log rows do show the kind.
- **Inbox.** `kind` is optional on the list and detail types (the API always sends it; a missing one is an ordinary message) and on the filters, so existing code and tests needed no change. A CV request has a "CV request" badge in the list and in the detail, and the list has a "Show" choice (All messages, CV requests) kept in the address as `?kind=cv_request`, in every folder and message link, and sent to the API. Any other `kind` in the address is dropped. A request with no name is shown as "No name given" (list, detail and any saved contact), because the link text must never be empty. Reply by email is unchanged.
- **Tests.** The browser tests use the API's test server with one seeded live CV of two pages (`api/tests/e2e_server.py`, `seed_cv`) and its own CV folder; the admin tests upload copies of that same file and put the first one live again, so the public tests see the same pages whichever is live. The matrix runs the public block, the viewer and the admin page in every browser with axe; Firefox's axe crash is not skipped there (see PROGRESS.md).

## Phase 5-1: abuse counters, alerts and access review data (API)

- **No email yet.** The site still sends no email. SPEC 10.15 asks for alerts by email; that waits for an email provider, which is a new service the owner has not chosen yet. Until then alerts go through the existing pluggable notifiers (`core.notify`): a new `DatabaseNotifier` records each alert for the admin, and the `LogNotifier` (set through `NOTIFIERS`) writes it to the log, where a log-based alert can pick it up. No mail library is added. An email notifier later is one more class in `NOTIFIERS`.
- **The database notifier does not count as telling the owner.** It is registered first in `settings.NOTIFIERS`, always on, and marked `in_band`. Anyone holding the admin could read and dismiss an alert there, so `send_required` still needs at least one notifier that is not in band: with only the database one, vital actions are refused as before. The database notifier is best effort: if it fails, the failure is logged (event name and error type only), counted as `notice_failed`, the notice still goes to the other notifiers and the action goes ahead. Its insert has its own savepoint, so it cannot break the transaction that sent the notice; if that transaction rolls back (a required notice not delivered), the alert goes with it.
- **Abuse counters** (`abuse_counts`, migration 0024): one row per UTC day and kind, counts only. Kinds: `rate_limited` (every 429: public read cap, admin request cap, sign-in cool-downs, contact and CV request limits, CV link limits, the upload cap), `blocked_sender`, `turnstile_failed` (contact form, CV request, CV link), `rejected_form` (a public form that fails validation or cannot be read), `spam` (links, repeat or score), `honeypot_or_timing`, `login_failed` (sign-in, bootstrap and recovery failures), and three more: `elevation_failed` (a failed passkey confirmation), `guard_refused` (the request guard's 403 for a wrong origin or no valid Access token, and its 413), and `notice_failed` (above). Each place adds one, once. A failed sign-in during the global cool-down is counted as `login_failed` only, though it is answered 429.
- **One statement per count.** `UPDATE abuse_counts SET count = count + 1` for the day and kind. The first count of a day finds no row, so the day's rows are made at zero (`INSERT ... ON CONFLICT DO NOTHING` through the ORM) and the same UPDATE runs again; no count is lost when two requests race. A count that fails is logged and the request goes on with the answer it would have had; the check itself still fails closed as before.
- **Write cost.** Each refusal is now one small UPDATE on one row. Under a flood these take turns on that row's lock. The edge limit comes first and each count is a tiny transaction, so this is accepted for one site; if it ever matters, count in Redis and add the totals to the table once a day.
- **Retention.** Counts are kept 365 days (`abuse.KEEP_DAYS`), the 12 months SPEC 6.2 gives messages; they hold no personal data, so nothing shorter is needed. The daily job removes older days in one DELETE under the same lock and in the same transaction; the audit entry gains `abuse_counts_deleted`.
- **Grants.** `abuse_counts`: select, insert, delete (for the daily job), update of `count` only. `alerts`: select, insert, update of `seen_at` only; no delete (at most 25 can be made a day; a retention rule can come later).
- **Abuse summary** `GET /api/v1/admin/abuse` (session): `from` and `to` (dates; default the last 30 days up to today; at most 366 days), `kind` (one kind). Answers the kinds, the total for each and a per-day series with zeros filled in. Unknown or repeated parameters are refused.
- **Alerts** (`alerts`, migration 0025: time, kind, fixed summary, seen time). Kinds and triggers, with thresholds in settings:
  - `failed_sign_ins`: 5 failed sign-ins (login, bootstrap, recovery) or passkey confirmations in 15 minutes, across all clients (`ALERT_SIGN_IN_FAILURES`, `ALERT_SIGN_IN_WINDOW`). A sign-in lockout notice is shown as this kind too.
  - `passkey_added`: a passkey added through a vital action, the first passkey at bootstrap (a new best-effort notice), or with the recovery key.
  - `vital_action_requested`: every request.
  - `rate_limit_storm`: 100 rate-limit refusals in 10 minutes (`ALERT_RATE_LIMITED`, `ALERT_RATE_LIMITED_WINDOW`).
  - `error_spike`: 20 answers of 500 or more in 5 minutes (`ALERT_SERVER_ERRORS`, `ALERT_SERVER_ERRORS_WINDOW`), the guard's 503s included.
- **How thresholds are counted.** A Redis counter per kind for a fixed window; the notice is sent when the count reaches the threshold exactly, so a window raises it once. Redis down: nothing is counted, and that is logged. Server errors are counted by `core.alerts.ServerErrorMiddleware`, second in `MIDDLEWARE` (after Django's security middleware, which a header test keeps first and which never answers 5xx): one Redis INCR per 5xx answer and no work for any other answer. That is the cheapest place that sees every answer.
- **No flood.** A threshold kind does not alert again inside its own window (checked against the alerts table), and no kind gets more than 5 alerts a UTC day (`ALERT_DAILY_CAP`). A threshold alert held back is not sent to any notifier. A vital action or new passkey past the cap still goes to the other notifiers (it is required there) but is not recorded again. If the database check fails, the threshold notice is sent anyway.
- **No personal data in an alert.** The summary is fixed text built from numbers and values from fixed lists (a vital action's kind in words; anything else is "a change"). The passkey name, ids, addresses, emails and message text never go in it. Logs for alerts and counters carry the kind and the error type only.
- **Alert routes** (session): `GET /api/v1/admin/alerts` (`unseen=1`; `limit` 1 to 100, default 50; `before` an alert id; newest first; with the unseen count) and `POST /api/v1/admin/alerts/<id>/seen`. Marking seen is an owner action, so it is audited (`alert_seen` with the id and kind), as the inbox's own changes are. Raising an alert is not audited: each comes from something already in the audit log, or from anonymous traffic.
- **Access review** `GET /api/v1/admin/access` (session): sessions (no ids or hashes; revoke all exists), passkeys (with the id the existing `revoke_passkey` vital action takes), the `app_rw` and `migrator` roles, the deploy pipeline, the Pages deploy hook, the Cloudflare API token, Cloudflare Access and the recovery key. Each has can, cannot, credential, expiry, last use and whether it can be revoked here. The Pages deploy hook is listed as well, since it is a secret the app holds.
- **The database rights come from the database.** For every model table and `django_migrations`, the page asks Postgres `has_table_privilege` for each table privilege, `has_any_column_privilege` and `has_column_privilege` for rights on some columns only, and `has_schema_privilege` for CREATE, all as ORM expressions on the owner row (no hand-written SQL). The "can" lines group tables with the same rights; "cannot" lists each right with the tables that lack it. A test compares the page with `information_schema.table_privileges` and `column_privileges` after `grants.sql`, and another changes a grant and checks that the page follows. The page says whether the API is connected as a member of the role; a superuser connection is reported as a warning instead, since a superuser is a member of every role.
- **Not checked by the app**: what the deploy pipeline, the Cloudflare token and the deploy hook are allowed to do (their scopes live in Google Cloud IAM and Cloudflare), the Cloudflare Access policy itself, and where the recovery key is kept. The page gives a fixed description and says so. It does check whether each secret is set (never its value), when the deploy hook was last called, when the recovery key was last used, and that this request passed Access. `docs/ACCESS.md` covers rotation and the quarterly review.

## Phase L: local development mode

- **Outside the app.** Local mode is a launcher, `api/devmode` (`python -m devmode check|serve|seed|drop`). Nothing in `config/`, `core/`, `manage.py` or `gunicorn.conf.py` imports or names it (a test parses every file), a fresh process importing `config.wsgi` has no `devmode` module and the real key lookup, and `api/.dockerignore` leaves it out of the image (the Dockerfile copies `config` and `core` only anyway). Coverage settings omit it. `core/access.py` and `core/guard.py` are unchanged.
- **How the gate is stood in.** In the launcher process only: a 2048-bit RSA key made at start and held in memory, `core.access.fetch_signing_key` pointed at its public key, and a WSGI wrapper that drops any `Cf-Access-Jwt-Assertion` the client sent and, for a request from 127.0.0.1 or ::1, adds a token signed with that key: RS256, 60 seconds, audience `portfolio-local-dev`, issuer `https://dev.cloudflareaccess.invalid`, email `owner@local-dev.invalid`. The real check still verifies every claim. `.invalid` never resolves, so without the patch no key for that team can be found; tests show the real lookup refuses the dev token and that the dev token does not fit production settings.
- **Guards, fail closed.** Before setting anything: refuse if `CLOUDFLARE_PURGE_TOKEN`, `CLOUDFLARE_ZONE_ID`, `PAGES_DEPLOY_HOOK_URL`, `GCS_MEDIA_BUCKET`, `GCS_CV_BUCKET` or Cloud Run's `K_SERVICE`, `K_REVISION`, `K_CONFIGURATION` is set; if `TURNSTILE_SECRET_KEY` is set and is not one of Cloudflare's three test secrets; if `SITE_ORIGIN` is set and is not `http://localhost` or `http://127.0.0.1`; if `MEDIA_STORAGE`, `CACHE_PURGER`, `SITE_DEPLOYER` or `DJANGO_SETTINGS_MODULE` names anything but the local choice. The database (`DEV_DATABASE_URL`, default the test container) must be `postgres://`, named `..._dev`, on a loopback host (a name counts only if every address it resolves to is loopback; a failed lookup is a refusal). Redis (`DEV_REDIS_URL`, default database 13) must be `redis://` on loopback and not 14 or 15, which the tests empty. The server binds to 127.0.0.1 only, port 1024 to 65535. After `django.setup()` the loaded settings are checked again (DEBUG on and set by the launcher, and the same database, Redis, origin, Turnstile, storage, purger, deployer and team rules); a setting that is missing or cannot be read is a refusal. Each refusal prints its reasons and exits 2.
- **Dev values.** Fixed dev-only secret and audit keys (they work only against a `_dev` database on this PC; the audit key must stay the same across runs for the chain), `DJANGO_DEBUG=1`, `SITE_ORIGIN=http://localhost:3000`, Cloudflare's always-pass Turnstile test keys with the real verifier (the widget needs the network anyway), `LogNotifier`, `LogPurger`, `LogDeployer`, and local media and CV folders in `api/.devmode`. The set-up token is random on each start and written to `api/.devmode/bootstrap-token` (git-ignored); only its SHA-256 is in the environment.
- **Server.** Django's own development WSGI server (`django.core.servers.basehttp.run`, which `runserver` uses), threaded, no reloader, so the wrapper can sit around the app. It is not for production, and here it never listens beyond loopback.
- **Database.** The test Postgres container (`portfolio-test-db`, 55432) holds `portfolio_dev` beside `portfolio` and `portfolio_e2e`. The launcher creates it if missing, migrates, and applies `db/roles.sql` and `db/grants.sql`, so the access review shows real rights. The browser-test server does not apply grants; this does, as production would. The connection is the container's superuser, which the access review reports as a warning, as it should.
- **Seed** (`python -m devmode seed`): SAMPLE content through the admin's own functions (draft, then Publish), checked by the same serializers: intro, about, two projects with a case study, experience, education, skills, contact, links, a custom palette copied from a preset, settings in pick mode, a two-page generated PDF set live with all three CV switches on, two inbox messages (one a CV request, senders at example.com), five abuse counts and two alerts. Every piece of text starts with SAMPLE; tests check this and run the privacy scan. Idempotent: each part is added only if missing, and sections and settings are never touched once present. `--reset` deletes content, media, CV versions, messages, contacts, blocks, counts and alerts (files only inside `api/.devmode`), empties Redis 13 and seeds again; the owner, passkeys, sessions and audit log stay. `--if-new` seeds only a database the same run created (used by `start`). `drop` deletes the database and the local files. All of them refuse a database not ending in `_dev`.
- **PDF helper shared.** The browser-test server's PDF generator moved to `tests/pdfs.py` as `text_pdf(pages, label)` and both use it; its output for the browser tests is unchanged.
- **Web.** A build plus `scripts/serve-static.ts`, not `next dev`: the static export with its `_headers` CSP is what Pages serves, and `next dev` applies neither. The build gets `API_BASE_URL=http://localhost:8000`, `SITE_ORIGIN=http://localhost:3000`, `TURNSTILE_SITE_KEY=1x00000000000000000000AA`, and `CF_PAGES` cleared. The CSP already allows the API origin and Turnstile from these values, so no header or CSP changed. Publish only logs locally (`LogDeployer`); `scripts/dev.ps1 refresh` rebuilds and restarts the site server (the server reads `_headers` when it starts, so a rebuild needs a restart).
- **Scripts.** `scripts/dev.ps1` (start, stop, status, refresh, reset, reset -Everything), `scripts/dev-web.ps1` (build, serve, stop, refresh) and `scripts/dev-common.ps1`. No `.env` file is read. Background processes start through `cmd /c` in a hidden window with their output in `api/.devmode/run/*.log`, so they share no handles with the caller. They are stopped together with their child processes (`taskkill /T`), because the venv's `python.exe` starts a second process. A recorded process id is used only if it is still the expected `cmd` process. Environment variables are set only while a child starts, then put back. Resets ask for `yes` unless `-Yes` is given.
- **Containers left running on stop.** The tests share them.

## Phase 5-2: abuse overview, alerts and access review (web)

- **Admin only, nothing public changes.** Three pages under `/desk` (`abuse`, `alerts`, `access`), after CV in the navigation. No dependency added: answers are checked with zod, which the admin already uses. The check is strict where it matters (`lib/admin/answer.ts`): an answer of the wrong shape throws `UnexpectedAnswer`, which `describeError` words as "not what this page expected", so a page shows an error and never an empty screen that looks like "nothing wrong". An empty list of principals counts as wrong, since the owner always exists.
- **Only known fields are kept.** The access answer is parsed with an explicit shape, so a field the API adds later is dropped, not rendered. Sessions show times and "this session" only (the API sends no ids or hashes); passkeys show their name. A browser test also walks the live answer for any key naming a secret and any long random value, and checks that the page text holds none of the test server's tokens.
- **Abuse overview.** The range is two date fields (default the 30 days up to today in UTC, as the API counts days), checked in the page with the API's own limit (366 days) before it asks. Totals and per-day counts are two real tables with captions. The per-day "bar" is an inline SVG `rect` inside an `aria-hidden` cell, because the admin's CSP has no `'unsafe-inline'` for styles, so a width in a `style` attribute would be refused; the numbers are in the table, so the bar adds nothing a screen reader needs. Bars are scaled to the busiest day, with a 2 percent sliver for any non-zero day. Each kind has a plain label and one sentence; the page says these are counts only and hold no addresses or messages.
- **Alerts.** Newest first, 20 at a time, with "Show older alerts" using the API's `before` cursor (a page-number pager does not fit a cursor). "Unseen only" is a checkbox sent as `unseen=1`. "Mark seen" is a button on each unseen alert, tied to its summary by `aria-describedby`; after it, focus goes to the same alert (all view), or to the next alert still waiting, else the heading (unseen view, where the row disappears), and a status line says so. Unknown kinds are shown as "Other alert" with the API's summary.
- **Unseen count.** `AdminApp` reads it with the session check (`GET /admin/alerts?limit=1`) and the Alerts page refreshes it on load and after Mark seen. A count that cannot be read shows "?" with text for screen readers, never nothing; a failed count does not make the admin "unavailable". There is no separate desk home page: `/desk` redirects to Sections, so the count in the navigation, which every desk page shows, is where the owner sees it first.
- **Access review.** One card per principal: can, cannot, credential, expiry, last used. "Not checked by the app" appears on exactly the principals the API marks `checked_by_app: false`, and their last use is "Not known" (not "never"). A principal whose warning is set shows it in its card, and a page-level alert states that the connection is a superuser and must never be so in production. Sessions and passkeys link to `/desk/security` (sign out everywhere, remove a passkey) instead of repeating those flows. Nothing is stored for "last reviewed"; the page says a quarterly review is the plan and points to `docs/ACCESS.md`.
- **Browser tests.** `api/tests/e2e_server.py` gains `seed_abuse_and_alerts`: abuse counts on days before today (the browser tests add to today's row), two unseen alerts, one seen and 22 older seen ones (so there is a second page). The access test uses the real answer; the test database is the container's superuser, so the warning shows there.

## Phase 5-3: email notifier (Resend)

- **Provider: Resend.** A JSON API with one key, sending-only keys, SPF and DKIM for our own domain, and a free plan that covers this site. Its pricing page on 2026-11-27 lists the free plan at 100 emails a day and 3,000 a month, 3 domains and 30 days of data retention. Brevo is the alternative if Resend's free plan changes or it stops delivering; swapping it is one more notifier class.
- **No new dependency.** `core.notify.ResendNotifier` posts with `urllib.request`, as `core.purge` and `core.deploy` already do. One POST, 5 second timeout, no retries. Redirects are refused, so the key is never sent on to another address. Any transport error, timeout or answer outside 2xx raises.
- **Fail closed is kept.** A required notice (`send_required`) whose email fails is `Undelivered`, and the vital action, new passkey or recovery is refused or undone, as before. If any of `RESEND_API_KEY`, `NOTICE_EMAIL_FROM` or `NOTICE_EMAIL_TO` is empty the notifier raises. It is not in the default `NOTIFIERS`: production names it there. `notify.send` tells every notifier before it raises the first failure of one outside the site, so the order does not matter and a failing email never keeps the log or the admin alert from recording the notice (changed after the first version, which stopped at the first failure).
- **Emailed events.** Required: `vital_action_requested`, `passkey_added` (through a vital action), `passkey_revoked`, `recovery_used`. Not required: `failed_sign_ins`, `rate_limit_storm`, `error_spike`, `lockout`, `passkey_added` at bootstrap, `sessions_revoked`, `access_revoked`. Any other event is not emailed.
- **Daily budget of 20 for notices that are not required** (`NOTICE_EMAIL_DAILY_BUDGET`), a per UTC day counter in Redis. Required notices are always attempted and never counted, so an alert storm cannot use up the 100 a day that vital actions need. Over the budget, or with the counter unreadable, the email is skipped and counted as `notice_skipped`; the alert is still recorded in the admin and the log. The counter is checked only for notices that are not required.
- **Plain text, no links.** Subject and body are fixed words, the event name, a UTC time, numbers, values from fixed lists and a passkey name that is short plain text (a name with `@`, other symbols or a long unbroken run is shown as "(name not shown)"). No HTML and no links, since the admin address is not decided yet; the cancel path and action id are left out. Tests send addresses, message text, session tokens and secrets through every field and check none reaches the request.
- **Logging.** Only the event name and the error type or status are logged; never the key, the headers or the addresses.
- **Local mode refuses it.** The launcher refuses `RESEND_API_KEY`, `NOTICE_EMAIL_FROM`, `NOTICE_EMAIL_TO` and `ResendNotifier` in `NOTIFIERS` (exit 2), before and after Django starts.
- **`notice_skipped` is a new abuse counter kind**, with a label on the abuse overview, so the owner can see when the budget was reached.

## Phase 6A: code hardening

- **At most 5 passkeys** (`ADMIN_MAX_PASSKEYS` in settings, a fixed value like the other limits, not read from the environment). A passkey that could never be added should not start a 24-hour wait or send a notice, so `add_passkey` is refused with 409 `passkey_limit` at the request, before anything is queued, and checked again at the registration options and inside the run, since another passkey could be added while it waited. Removing a passkey deletes its row, so every stored passkey counts and a removal frees a place at once. A pending add does not hold a place: the run checks again. Bootstrap and recovery are not affected (they start from none and leave one). The Security page says "up to five" and words the refusal; change both if the setting changes.
- **Production refuses a Turnstile check that is not real.** Production is detected by `K_SERVICE`, which Cloud Run sets in every container and which local mode already refuses as a production value; `settings.PRODUCTION` reuses it. With it set, the settings raise `ImproperlyConfigured` while loading, so gunicorn's workers fail to boot and Cloud Run never routes to the revision: an empty `TURNSTILE_SECRET_KEY`, any of Cloudflare's dummy secrets (`1x`, `2x`, `3x` then zeros and `AA`, matched by shape so a new one is caught too), or any `TURNSTILE_VERIFIER` other than `core.turnstile.CloudflareVerifier`. The error names the setting, never the value. Outside production (tests, CI, docker-compose, local mode) the same values load as before. A Cloud Run job (`CLOUD_RUN_JOB`, no `K_SERVICE`) is not checked: it serves no forms.
- **A Pages build needs the data-request address.** `privacyEmailFrom` throws when `CF_PAGES` is set and `NEXT_PUBLIC_PRIVACY_EMAIL` is unset or blank, in `next.config.ts`, the same place and the same way a Pages build without `SITE_ORIGIN` fails (the Turnstile site key is read there too, but a Pages build without one shows no form instead of failing). Pages keeps the last good build, so a failed build is safe. Local, test and browser-test builds do not set `CF_PAGES`, so they still build and the Privacy page still says the address comes before launch. `check:build-refuses` gains the case and clears the variable from its builds unless a case sets it.
