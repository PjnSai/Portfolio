# Decisions

Short record of choices made while building, with the reason. Newest last.

## Phase 0

- **Django 5.2 (LTS) on Python 3.12.** The spec asks for the current LTS release. Python 3.12 matches the local toolchain and is supported by 5.2.
- **Python dependencies pinned with hashes** (`pip-compile --generate-hashes`; edit `requirements*.in`, then recompile). An altered package fails the install rather than being used.
- **No database URL library.** `DATABASE_URL` is parsed with the standard library in `config/settings.py`; one dependency fewer.
- **Redis client not installed yet.** Nothing uses it until rate limiting arrives in phase 1.
- **API denies by default.** The default DRF permission is `IsAuthenticated`; public endpoints opt in with `AllowAny`. JSON renderer and parser only, so there is no browsable API.
- **No default secret key.** The API refuses to start without `DJANGO_SECRET_KEY`. Tests set their own in `tests/settings.py`.
- **Web image is distroless** (non-root, no shell). **API image is `python:3.12-slim`** running as a numeric non-root user on a read-only filesystem. It still contains a shell; moving it to a shell-less base is left for the hardening phase.
- **Gunicorn control socket disabled.** It is not needed and would require a writable home directory.
- **Base images are pinned by tag for now.** Pinning by digest is left for the hardening phase; Dependabot watches them meanwhile.
- **No web fonts or placeholder styling.** Design work starts in phase 3.
- **End-to-end tests run against the standalone build**, the same server the container runs.
- **`/healthz` on Cloud Run.** The Google front end may intercept some paths ending in `z` on `*.run.app` URLs. To be confirmed in phase 7 before health checks rely on it from outside.

## Phase 1

- **No Django auth, sessions or admin apps.** Passkeys and sessions live in `core`, so there is no password table and no code path that could accept one.
- **Cloudflare Access is checked by the API itself**, on every admin request and before the URL is resolved. The API does not trust that a request came through Cloudflare; it verifies the signed token (RS256 only, audience, issuer, owner email). Unknown admin paths therefore look the same as known ones.
- **One place decides admin authorisation.** Every admin view is wrapped with `admin_route(level)`; the guard refuses any admin URL without a declared level, so a new route is denied until someone chooses its level.
- **CSRF: three independent checks.** State-changing requests need an exact `Origin`, `Sec-Fetch-Site: same-origin`, and a CSRF token. (Token handling replaced below, under "Django built-ins".)
- **Session token is random, stored as SHA-256.** A plain hash is enough because the token is 256 random bits; there is nothing to brute-force.
- **Passkey confirmation lasts five minutes** and issues a new session token. It is not consumed by one action, so several vital actions can be requested in one sitting.
- **Sign-in failures are indistinguishable.** No credential list is sent, and an unknown passkey is still verified against a throwaway key so the work is the same.
- **Rate-limit counters in Redis, cool-downs in Postgres.** A cool-down must survive a Redis restart; a counter need not. Addresses are stored only as a keyed hash.
- **The global cool-down never blocks a valid passkey.** Failures from many addresses start it. It closes bootstrap and turns every failed sign-in into a 429, but `login/options` stays open and a correct passkey signs in. Otherwise anyone able to reach the sign-in route could lock the owner out for as long as they kept failing. During it all failures get the same 429 after the same signature check, so it reveals nothing about which passkeys exist. A client's own cool-down still refuses even the right passkey, and still ends after 15 minutes.
- **The 503 for a missing dependency is admin only.** The guard uses neither the database nor Redis for a public request and does not convert errors raised by public views. Public reads get their own fail-static handling in phase 3.
- **Vital actions: fixed 24-hour wait, then a 7-day window.** The delay is a constant on the server; fields the client sends for it are ignored. An action not run within seven days of maturing expires. Cancelling needs only a session, so a cancel is always easier than a run.
- **A vital action is refused if the owner cannot be told.** This includes the case where no notifier is configured. The request, its audit entry and the notice succeed or fail together. A new passkey is likewise undone if its notice fails.
- **Notifiers are chosen by the `NOTIFIERS` setting** (comma-separated dotted paths). `core.notify.LogNotifier` writes notices to the log and is the only one shipped so far; an email notifier arrives in phase 5. Until then the notice is only as out-of-band as the log alerts are.
- **Permanent delete covers messages only**, by allow-list (sections and items from the trash joined in phase 2A). Media and CV files join when their stored objects can be removed with them (phases 2 and 4). Auth and audit tables can never be named.
- **Adding a passkey is two steps after the wait**: options, then run with the new credential. A failed registration leaves the action ready to try again.
- **Audit listing is paged by sequence number**, newest first, at most 100 per page. Unknown or repeated query parameters are refused rather than ignored.
- **Audit chain limit.** Removing the newest entries leaves a shorter chain that still verifies. Catching that needs the latest sequence number and hash kept somewhere else; planned with backups in phase 7.
- **Web CSP uses a per-request nonce**, set in `web/proxy.ts` (the Next.js 16 name for middleware) with no matcher, so every response carries the headers. Next.js reads the nonce from the request and adds it to its own tags. The cost: every page is rendered per request (`connection()` in the root layout), so pages cannot be cached at the edge as they are. To be revisited in phase 3, when public pages need caching; hash-based CSP is the likely answer.
- **No `upgrade-insecure-requests` in the CSP.** HSTS does that job, and the directive would break tests against the local HTTP server.
- **`npm run typecheck` runs `next typegen` first.** The layout uses a generated type, and CI type-checks before it builds.
- **CI runs Postgres and Redis as job services**, the same major versions as Docker Compose. Their password is a fixed throwaway value: the services exist for one job and hold no real data. The database role tests need a superuser to create roles.
- **One owner row, enforced by the database.** `admin_owner` holds a single row made by a migration: a unique boolean that a check constraint pins to true. The app login has SELECT and column-level UPDATE only, so a bug or injection in the app cannot add an account. Sessions carry a foreign key to it.
- **Bootstrap closes for good**, recorded in `admin_owner.bootstrapped_at` under a row lock, not inferred from whether a passkey exists. Removing every passkey must not reopen it.
- **Access email is compared exactly.** Cloudflare sends the address the policy matched; folding case or trimming would only widen what is accepted.
- **Recovery key instead of a database reset.** 256 random bits, shown once at bootstrap, stored with Django's password hasher (see below), single use and replaced on use. It is the only way back after `access/revoke-all` or losing every passkey, so it needs Access, counts towards the sign-in cool-down and is refused if the owner cannot be told. A password-style reset link was rejected: it would add a second way in that needs no passkey.
- **Revoking sessions or all access runs at once, and a failed notice does not stop it.** These only take access away, so delaying them or making them depend on the notifier would help an attacker, not the owner. Both need a fresh passkey confirmation so a stolen session cannot lock the owner out. Revoking a single passkey goes through the 24-hour vital action instead, because a stolen session plus confirmation could otherwise remove the owner's other keys quietly.
- **`NOTIFIERS` defaults to `core.notify.LogNotifier`** in Compose and `.env.example`, so a fresh setup does not refuse every vital action. The settings default stays empty: production must name its notifiers.
- **Ruff rules S106 and S107 are off for tests.** They flag the fixed bootstrap token the tests use on purpose.

## Django built-ins

- **Django's SecurityMiddleware and XFrameOptionsMiddleware set HSTS, nosniff, Referrer-Policy, COOP and X-Frame-Options.** `core.headers` now adds only what Django lacks: CSP, CORP, Permissions-Policy and the `no-store` default for Cache-Control. `SECURE_PROXY_SSL_HEADER` trusts `X-Forwarded-Proto`, which Cloud Run sets itself; HSTS is sent on HTTPS requests only, as browsers ignore it over HTTP anyway.
- **Django's CsrfViewMiddleware checks the CSRF token on every state-changing request, including the six sign-in routes.** The secret lives in an HttpOnly `__Host-csrf` cookie (Secure, `SameSite=Strict`, no expiry); the page reads a masked token from `GET /api/v1/admin/csrf` or from the sign-in response and sends it in `X-CSRF-Token`. The secret is replaced on sign-in and on passkey confirmation. The Fetch-Metadata and exact-Origin checks in `core/guard.py` stay on top. `/healthz` is exempt because it is GET only, as the DRF views already are.
- **The recovery key is hashed with `make_password` (PBKDF2) and checked with `check_password`.** It is random enough for SHA-256, but the spec uses Django's hasher for any secret a person keeps, and the cost is one slow hash on a rare route. The column grew to 128 characters. A recovery key stored as plain SHA-256 is no longer accepted; none exists outside development, where bootstrap issues a new one.
- **Sessions stay custom.** Django's session framework would bring `django.contrib.sessions` without giving what 10.5 needs: 256-bit ids stored only as a hash, a 15-minute idle and 8-hour absolute timeout, rotation that keeps the absolute timeout, revoke-all, and a foreign key to the single owner row.
- **Authentication stays custom, and `django.contrib.auth` is not installed.** Sign-in is a passkey behind Cloudflare Access for one owner row. Django's user model would add a password column, users, groups and permissions that nothing uses, and a second way in to defend. Only `django.contrib.auth.hashers` is imported, which needs no models.
- **Session and bootstrap tokens stay hashed with SHA-256.** Both are 256 random bits, so there is nothing to brute-force and a slow hasher adds nothing. Session tokens are looked up on every admin request, which a slow hash would make expensive.

## Phase 2A

- **Items are one table, `section_items`, with a JSON draft validated per section type.** Each section type that holds items (projects, experience, education, skills, gallery, links) has a strict DRF serializer in `core/serializers.py`. One table keeps add, hide, reorder, trash, publish and restore the same code for every type. The typed tables from phase 1 (`projects`, `experience` and so on) were dropped after phase 2B (see below).
- **Serializers refuse unknown fields instead of ignoring them.** This is the mass-assignment guard: a request cannot set ids, positions, visibility, published copies or timestamps by adding keys. Strings must be strings (no numbers turned into text), booleans must be `true` or `false`, and control characters are refused.
- **What is live at once and what waits for Publish.** Section order, show and hide, and moving a section to the trash apply at once, so the owner can take something down quickly. Everything inside a section (title, text, items, their order and visibility) is a draft until the section is published.
- **A version is the whole section.** Publishing stores the section's draft and its live items (with order and visibility) as a numbered revision, and the public copy holds only the shown items. Restoring a version puts it back as the draft; items added since go to the trash rather than being deleted, so nothing is lost. Items deleted for good since cannot come back.
- **Trash: restore for 30 days, then `manage.py purge_trash` deletes.** It is meant to run daily (scheduled in phase 7). Permanent delete before that is the vital action, allowed only for something in the trash and refused if it was restored meanwhile. One-of-a-kind sections (intro, contact) cannot be restored next to a live one.
- **Caps: 40 sections, 200 items per section.** They bound storage and page work. Adding a section or item takes the owner row lock so the caps and the one-of-a-kind rule cannot be raced.
- **Listings are page-numbered, 25 per page.** The audit log keeps its sequence-number paging. Unknown or repeated query parameters are refused, as for the audit log. The admin loads every page of a list it reorders (at most 40 sections, or 8 pages of items).
- **Flagged audit events are a fixed list** (`core.audit.FLAGGED`: failed sign-ins, lock-outs, recovery, passkey changes, revocations, vital actions), not a stored column, so the hash chain is unchanged.
- **Admin at `/desk`.** Not linked from the public site, `noindex` in the page and in `X-Robots-Tag`, and `Cache-Control: no-store`. Cloudflare Access must cover `/desk/*` and `/api/v1/admin/*`. The name is not a secret.
- **The web service passes `/api/v1/*` to the API itself** (`app/api/v1/[...path]/route.ts`), reading `API_URL` at run time, so the admin and the API share one origin and the API's exact-Origin and Fetch-Metadata checks hold. Only the headers the API reads are forwarded. Bodies over 1 MB, dot segments and over-long paths are refused. With no `API_URL`, or no answer, it returns 503.
- **Reorder uses Up and Down buttons, not drag.** They work with a keyboard, a screen reader and on a phone. Drag can be added later on top.
- **Passkey confirmation is a dialog with its own button.** Some browsers only allow a passkey prompt straight after a click, so the admin does not start one by itself after a refused request.
- **Browser tests run the real API** through `api/tests/e2e_server.py`: a fresh `*_e2e` database each run and a throwaway RSA key in place of Cloudflare's key list. The token is still checked in full; nothing in the API's checks changes. The CI web job gets Postgres, Redis and Python for this.
- **No new dependencies.** WebAuthn in the browser is about 100 lines in `web/lib/admin/webauthn.ts` rather than a library.
- **Admin colours are CSS variables in `app/globals.css`,** swapped for the dark theme. Fonts fall back to system faces until the self-hosted fonts arrive with the public design in phase 3.

## Phase 2B: content editors

- **Content stays in `section_items` as JSON, one strict shape per type.** The editors did not need the phase 1 typed tables (`projects`, `project_images`, `project_fields`, `tags`, `experience`, `education`, `skill_groups`, `skills`, `links`). They were unused and are dropped by migration `0006_drop_typed_content`, with their models and grants; `media` stays, because image slots point at it. All content now lives in `section_items`.
- **Section edits are merged, then the whole draft is checked.** A PATCH sends only the fields that changed; the API puts them over the stored draft and validates the result against the section type's shape, so a partial edit cannot skip a required field such as a photo's alt text.
- **Project shape.** Title, short description, case study (Markdown), status (live, demo, local, in progress), created month (may be empty while in progress), category for the filter, card colour from a fixed list (orange, blue, pink, olive, yellow, black), tags (30, each once), links (10, kind demo, code or other, https only), label/value fields (20) and image slots (8). Experience gains tags; education gains a grade.
- **Image slots hold alt text now and a media id later.** The id must name a live row in `media`; until the media library exists it is empty and the admin says so. Alt text is required for every slot.
- **Markdown becomes React elements, never an HTML string.** `web/lib/markdown.ts` parses with markdown-it (CommonMark, HTML off) and builds elements from an allow-list: paragraphs, two heading levels under the section heading, lists, quotes, code, rules, emphasis and links. Raw HTML shows as text, images show as their alt text (pictures come from image slots), links are kept only for `https`, a site path or an anchor. There is no `innerHTML` anywhere, so Trusted Types has nothing to guard here. The public site in phase 3 uses the same function.
- **Two new web dependencies.** `zod` for client validation (SPEC 10.4 names it). `markdown-it` for parsing: widely used, small, and a hand-written parser would be riskier.
- **The privacy check warns; the API enforces the warning.** Email addresses, phone numbers (10 to 13 digits starting with 0 or +) and UK postcodes in anything Publish would put live are listed in the editor. Publish is refused with `409 privacy_check` unless the request says `confirm: true`. Hidden items are not checked because they are not published. False positives are possible; the owner decides.
- **Theme tokens: four colours per mode.** Background, text, accent and text on accent, for light and dark. Pairs checked: text on background 4.5:1, text on accent 4.5:1, accent against background 3:1 (WCAG AA for text and for interface parts). Colours are `#rrggbb` only, stored in lower case, never free CSS. Presets (orange, blue, olive) live in `api/core/theme.py` and are served with the settings, so there is one list. The editor shows ratios as you type and will not save a failing pair; the API refuses it too.
- **Settings are one row, drafted and published like a section,** with a numbered revision per publish. They hold title, description, contact form on or off, showcase layout and visitor switcher, SEO title and description for a fixed set of pages, a social preview image slot and the theme. Social links are not repeated here: they are the Links section.
- **Cache purge on publish** came in phase 2C (below).

## Phase 2C: media library and cache purge

- **One new dependency: Pillow.** It decodes and re-encodes images; nothing else in the standard library can. Google Cloud Storage and Cloudflare are each a few HTTPS calls with `urllib`, so no cloud SDKs.
- **The bytes decide what a file is.** Pillow opens JPEG, PNG and WebP only; the file name and the type the browser declares are ignored. SVG is refused (it can carry script), and so are GIF, BMP, PDF and anything else. Limits: 8 MB per file, 40 megapixels, one file per upload, 50 uploads a day.
- **Every image is drawn again from its pixels as WebP** at 480, 960 and 1600 px wide (never scaled up). Camera rotation is applied first, then EXIF, GPS, XMP, ICC profiles and anything after the image data are left behind. The original is not kept. Alt text (one line, up to 300 characters) is required at upload and on every edit.
- **File names are 128 random bits plus the width** (`<32 hex>-<width>.webp`). Storage refuses any key outside that pattern, and local disk also checks the resolved path stays in the store root.
- **Storage is an interface with save, read and delete.** `MEDIA_STORAGE=local` (development, tests, compose volume) or `gcs` (production: a private bucket, written with the Cloud Run service account's token from the metadata server). R2 can be added as a third class. If storage fails during an upload, the sizes already stored are removed and the API answers 503.
- **Visitors get images through the API, not from the bucket.** `GET /api/v1/media/<name>` serves a size only when the image is used by a published, shown section or the published settings, and is not in the trash; anything else is the same 404. Responses are `immutable` for a year, so after the first request the edge serves them. Unpublished images are visible only in the admin (`/api/v1/admin/media/<id>/file`, session needed, `no-store`).
- **`GET /api/v1/site` is the one public read of content:** published settings, the published copy of each shown section in order, and the image sizes they use. It is the document the public pages in phase 3 render from. `s-maxage` of a year because every change that goes live purges it; `stale-if-error` of a week, so the edge keeps serving the last good copy if the API is down (fail static).
- **Cache purge uses `purge_everything` on the zone** with a token that has only the Cache Purge permission. The site is small, so purging by URL is not worth the bookkeeping. It runs after section or settings publish and after the changes that go live at once (section order, show and hide, trash and restore, image trashed). The change is saved first; a failed purge is kept on the settings row, audited, shown as a banner with a retry button, and cleared by the next purge that works. `CACHE_PURGER=core.purge.LogPurger` (the default) only logs.
- **Request bodies are capped in the API guard too**, before anything reads them: 1 MB, or one image plus its form on `POST /api/v1/admin/media`. The web proxy applies the same two limits. Uploads are held in memory only.
- **Media in the trash cannot be deleted for good early.** The vital-action allow-list stays as it is; trashed images stop being public at once and `purge_trash` removes them and their files after 30 days.
- **Admin request cap raised from 120 to 300 a minute.** Each thumbnail on the media page and in the image picker is an admin request, so 120 was reached in normal use. The cap is per client, behind Cloudflare Access, so 300 still stops a runaway script.
- **Image slots pick from the library.** The editor shows a thumbnail of the chosen image, fills empty alt text from the library, and can change or clear the image. The media page lists 25 images per page.

## Phase 3A-0: static export on Cloudflare Pages

- **The web app is a static export on the Cloudflare Pages free plan; Cloud Run runs the API only.** Pages serves files from the edge with no request limit and no cold start, and the site needs no server: public pages change only on publish, and the admin is a client-side app. Pages Functions, SSR, middleware, route handlers, server actions and `cookies()`/`headers()` are not used, because they run on Workers and count against the free limits. `web/scripts/check-export.ts` fails CI if any appear. This replaces the web Cloud Run service and the `/api/v1` pass-through route of phase 2A.
- **Public pages are built from `GET /api/v1/site`** at build time, from `API_BASE_URL`. If the read fails, the build fails and Pages keeps the last good build (fail static). Without `API_BASE_URL`, or with `SKIP_SITE_FETCH=1` (container images built before their API runs), the site builds without content; on Pages (`CF_PAGES`) that is refused. `API_BASE_URL` is a public address; no secret reaches the build or the bundle, and CI checks the output for the values of secret-named variables.
- **The admin calls the API on its own host with `credentials: 'include'`.** The site and the API are hosts of one domain (for example the site and `api.` under it), so the `__Host-`, `SameSite=Strict` cookies still travel and the browser sends `Sec-Fetch-Site: same-site`. The guard now accepts `same-site` as well as `same-origin`, still only with the exact `SITE_ORIGIN`; admin reads with any other `Origin` are refused. A small CORS middleware (no new dependency) answers preflights for `SITE_ORIGIN` only, under `/api/v1/admin/` only, for the two request headers the admin sends. Cloudflare Access must cover the admin paths on both hosts and pass `OPTIONS` through to the API (set up in phase 7). Passkeys are unchanged: the relying party is still the site's host.
- **The API's `Cross-Origin-Resource-Policy` is now `same-site`,** so pages on the site's host can show the API's images. Other sites still cannot embed them.
- **Section editor at `/desk/sections/edit?id=`.** Section ids are made after the site is built, so `generateStaticParams` cannot list them; one static page reads the id from the query string.
- **Rebuild on publish through the Pages deploy hook.** Everything that calls the cache purge (publish, section order, show and hide, trash and restore, image trashed) then asks for a build. At most one call per two minutes, decided under a lock on the settings row; a change inside the window is kept as pending and goes out with the next change or with "Build the site now" in the admin. Each call and each debounced request is audited. The last call, its result and any pending change show at the top of the admin. `PagesDeployer` accepts only `https://api.cloudflare.com/client/v4/pages/webhooks/deploy_hooks/<id>`, so a wrong value cannot send the request elsewhere; errors are recorded by type only, so the URL is never logged. The hook only queues a build; whether the build passed is shown in the Pages dashboard. The cache purge stays, for `/api/v1/site` and media.
- **CSP by hash, written after each build.** Next.js puts several inline scripts in every page, and a static page cannot carry a per-request nonce. `web/scripts/write-headers.ts` hashes each page's inline scripts and styles and writes `out/_headers`: static headers and the 404 page's policy on `/*`, then each page removes that policy and sets its own. Pages' limits (100 rules, 2000 characters a line) fail the build if reached. `EXTRA_SCRIPT_HASHES` in `web/lib/security-headers.ts` is the place for a hand-written script (phase 3A-4). The file is generated into `out/`, not `public/`, because the hashes are only known after the build. The development server sends no policy.
- **Next.js prefetch files are renamed after the build.** The export writes nested pages' prefetch files as `__next.desk/sections/__PAGE__.txt` while the client asks for `__next.desk.sections.__PAGE__.txt`; on a static host the request never settles. `web/scripts/flatten-segments.ts` renames them, and the export check fails if a nested one is left.
- **`web/scripts/serve-static.ts` serves `out/` as Pages does** (`x.html` for `/x`, `404.html` with status 404, `_headers` rules in order, `!` removing a header). The browser tests build against the real API and run on it, and the web container uses it for Docker Compose and the `kind` demo. The scripts are TypeScript run by Node directly.
- **Fonts by `next/font/google`.** Bricolage Grotesque, Instrument Sans and IBM Plex Mono are downloaded while building and served from `/_next/static/media`; visitors never contact Google. No new dependency. The build needs network access to Google Fonts.
- **Image widths unchanged.** Phase 2C already stores WebP at 480, 960 and 1600 px (never scaled up; a smaller image keeps its own width as the largest size) and lists them in `GET /api/v1/site` and the media API. No migration was needed; `srcset()` in `web/lib/site.ts` builds the attribute with the API origin in front.
- **No health route on the web side.** Static files need none; the API keeps `/healthz`.
- **Terraform and Kubernetes.** None exists yet. When phase 7 writes it, Terraform covers the API Cloud Run service only; the Pages project, its custom domain, build settings and deploy hook are set up by hand in the Cloudflare dashboard. The Kubernetes manifests for `kind` keep both containers as a local demo.
- **Pages limits for `_headers` are checked twice.** The writer refuses more than 100 rules or a line over 2000 characters, and `check-export.ts` measures the written file again. Each page keeps its own rule while the page rules fit in 90; past that, the route pattern with most pages (for example `/projects/*`) is folded first into one rule holding the union of its pages' hashes and the 404 page's. Today: 15 rules, longest line 599.
- **A build fails if `GET /api/v1/site` is unreachable or answers an error,** so Pages keeps the last good build. A build where it answers but nothing is published goes ahead: `/desk` is in the same build, so refusing would stop the owner from ever publishing the first section (SPEC 17: placeholders, never blocking). The home page then shows the site title (or "Portfolio"), "Site coming soon" and a `noindex` meta tag, and no other public page is built. `web/scripts/check-build-refuses.ts` runs real builds against a stub API in CI: down and error must fail, empty must pass with the placeholder and `/desk`. The browser tests' API still publishes one section (`Seeded`).
- **The Next.js fetch cache is cleared before each build.** Next stores build-time fetch answers in `.next/cache/fetch-cache` and Pages restores `.next/cache`, so a build could reuse an old site document and never see an outage or an unpublish. The build check fills the cache with a good answer first, so reuse fails it.
- **CORS allows GET, POST and PATCH only,** the methods admin routes take; PUT and DELETE were dropped. `Vary: Origin` is on every admin response, with or without CORS headers.
- **A browser test fails if any prefetch request gets a 404,** so a Next.js upgrade that changes the prefetch file names is caught in CI.

## Phase 3A-1: palette data model

- **Palettes are rows in a new `palettes` table** (random UUID, name, kind `preset` or `custom`, light and dark slot sets as JSON, timestamps, `trashed_at`). Each mode fills thirteen slots: `bg`, `ink`, `surface`, `primary`, `on_primary`, `accent_1` to `accent_4`, `on_accent_1` to `on_accent_4`. The app role gets read and write on it in `db/grants.sql`.
- **Colours are `#RRGGBB`, stored in upper case.** Anything else is refused, including short hex, named colours, `url()`, `var()` and strings carrying CSS. The 2B rule was lower case; the spec now says upper.
- **Contrast pairs, in light and in dark:** `ink` on `bg` and on `surface`, `on_primary` on `primary`, each `on_accent_n` on `accent_n` at 4.5:1. (The 3:1 rule for `primary` against `bg` was dropped in 3A-2; see there.) Errors sit under the mode and read "Light: ink on bg is 4.48:1; it needs at least 4.5:1." `web/lib/admin/contrast.ts` does the same sums with the same wording.
- **Presets A to E are made by migration `0010_palette_data` with fixed ids,** so new settings can name Original (E) as the default. The dark sets and the slots the spec does not give (surface, on-colours, the accents of A to D) were chosen to pass every pair. Original's light primary was briefly `#E8551C` to pass a 3:1 rule against the cream; 3A-2 put it back to `#FF5A1F`.
- **Presets cannot be edited or deleted** (409 `preset`); duplicate one to customise. At most 12 custom palettes (409 `palette_limit`, checked under the owner row lock, and again on restore). Conflicts now carry a short `code` so the admin can explain them.
- **The choice of palettes is three settings fields:** `palette_mode` (`fixed`, `rotate`, `pick`; default `fixed`), `default_palette_id` and `enabled_palette_ids` (1 to 17, each once, each a live palette, the default among them). `POST /palettes/use` sets them; a settings edit checks the same rules.
- **Palette rows are drafts; settings publish takes a copy.** Publishing the settings stores the enabled palettes' colours with the published settings, so editing a palette changes nothing live until the next publish, and that publish runs the cache purge and the Pages rebuild. "Unpublished changes" compares the draft settings plus the enabled palettes. Palette names are checked for contact details like other published text; palette ids are not scanned, since a run of digits in one can look like a phone number.
- **Deleting a custom palette moves it to the trash** and takes it off the draft enabled list. The default palette (in the draft or on the live site) cannot be deleted (409 `default`). Trashed palettes are restored within 30 days or removed by `purge_trash`; like media they are not on the vital-action delete list.
- **`GET /api/v1/site` returns `palettes`:** only the enabled ones, as last published, each with id, name, light and dark. The settings carry the mode, default id and enabled ids. Before the first settings publish the list is empty.
- **The 2B theme moved into palettes and its field is gone.** A theme still equal to the 2B default becomes Original; any other becomes a custom palette (surface = background, accents from Original, so every pair still passes). The live copy is kept as it was. The 2B theme editor in /desk is removed; the palette editor comes in 3A-4.
- **Admin routes:** `palettes` (list, create), `palettes/use`, `palettes/<id>` (get, edit), `palettes/<id>/duplicate`, `palettes/<id>/trash`, `palettes/<id>/restore`. All go through `admin_route(Level.SESSION)`, so the route tests try each with no, expired, revoked and wrong sessions and without the CSRF token. Each change is audited (`palette_added`, `palette_duplicated`, `palette_changed`, `palette_trashed`, `palette_restored`, `palettes_chosen`).

- **The primary is a decorative fill only (owner's decision).** It has no contrast rule against `bg`; `on_primary` on `primary` still needs 4.5:1, and no button or control may rely on a primary fill alone: each carries an ink border or an ink label (the editor's preview shows this). So preset E's light primary is the spec orange `#FF5A1F` again (2.63:1 on the cream, now allowed).

The live copy changes at the next publish. E stays a normal preset. New settings start on A. Undoing 0011 puts E back as the default.
- **Shared contrast vectors** (`api/tests/contrast_vectors.json`) are checked by pytest and vitest, so the client copy in `web/lib/admin/contrast.ts` gives the same ratios and the same messages as the API. The API stays the authority; its 400 errors are placed next to the slot (or both slots of a failing pair).
- **Colour picker: react-colorful 5.8.1 (MIT, no dependencies, 0 audit findings).** Reason: the spec names it for the saturation square and hue slider, both keyboard operable sliders. It has no CSS file; it adds one fixed `<style>` element at run time, which the strict CSP blocked (checked in Playwright: the picker lost its layout). A unit test recomputes the hash from the installed package, so an upgrade that changes the CSS fails until the hash is updated.

- **Admin colours are set from JS, never in HTML.** Swatches and the preview set CSS variables through `element.style.setProperty`; the built `/desk` pages contain no colours (tested).
- **Editor layout:** `/desk/settings/palette?id=...` (one static page, like the section editor). Each slot is a labelled group with a 44 px swatch button, hex and R/G/B fields; opening the picker moves focus to its colour square, Escape returns to the swatch. Save is blocked while any pair fails. Leaving with unsaved changes asks first (closing the tab or following a link). The palette choice (mode, default, enabled) is a separate form on the settings page; the default is always enabled.
- **Trash page lists palettes** with Restore only; palettes are not on the vital-action delete list, so they leave after 30 days.
- **The browser test server raises the admin request cap to 1,200 a minute** (`api/tests/e2e_server.py` only). The suite is one client doing many sittings' work in about 30 seconds and had reached the production cap of 300, so it failed or passed depending on where a minute began. Production stays at 300 and `tests/test_guard.py` still tests the cap.

## Phase 3A-3: public tokens, components, navigation and layout

- **Palette tokens are an inline `<style>` written at build time** from the published palettes: `--c-<slot>` under `[data-palette="<id>"]` for light and inside `@media (prefers-color-scheme: dark)` for dark, with preset A on `:root` as the fallback before the first settings publish. `<html>` gets the published default's id. Ids must be UUIDs and colours `#RRGGBB` or the palette is left out, so nothing but colours reaches the CSS. The style is hashed into each page's policy like the inline scripts. Tokens are prefixed `--c-` so they cannot clash with the admin's variables.
- **Components use slot tokens only.** Card and tile colours are a `data-accent` attribute (`primary`, `1` to `4`, `ink`) mapped to slot pairs in CSS; no `style` attribute is written. The admin's card colours map as orange to primary, blue, pink, yellow and olive to accents 1 to 4 (Original's order), ink to ink.
- **Public pages are a route group `app/(site)`** with its own layout and stylesheet, under the shared root layout. They link with plain `<a>`, not `next/link`: each page is a complete static document, the nav script runs once per page and nothing is prefetched. The lint rule against `<a>` is off for these folders only.
- **One small client component, `NavEnhancer`** (0.9 kB gzipped), adds the burger menu, `aria-current` from IntersectionObserver, and focus on the target heading after a jump. Without JavaScript the nav links wrap onto a second row on a phone and every link works. Tabbing out of the open menu closes it.
- **Anchors come from the section type** (`#projects`, `#experience`), or the title for text and gallery sections, made unique and kept off `main` and `top`. Numbers count from 01 after the hero. With a contact section, the links section is shown inside it and not in the nav.
- **Project slugs come from titles** (`/projects/task-board`), with `-2` for a repeat. A renamed project gets a new URL; acceptable while there is no sitemap. A static export must build at least one case-study page, so with no projects one placeholder page (`/projects/none`, `noindex`) stands in.
- **Stat tiles count what is published** (projects, roles, qualifications, skills) and leave zero counts out. The About shape has no stats field and numbers are never typed in for the owner.
- **The hero photo is the About section's photo,** in the 4:5 primary block with an offset ink block. The CV button waits for the CV phase.
- **Markdown headings in seeds use `#`** for the level under the section heading, as the 2B mapping (`#` to h3, `##` to h4) expects.
- **Initial JavaScript on home is about 139 kB gzipped** (133.0 kB of module scripts, 5.8 kB inline payload); the 38.7 kB `noModule` polyfill is not loaded by modern browsers. No CI check measures this yet; it belongs with the release gate.
- **Browser tests seed one published section of each type** plus published settings (`api/tests/e2e_server.py`); Education is published empty to show its placeholder.

## Phase 3A-4: visitor palettes, light and dark, script hash, cache headers and rate limits

SPEC sections used: 4.2b, 4.5, 4.7, 4.9, 4.10, 7, 10.3, 10.4, 10.12, 11.1, 11.3, 14.

- **The visitor's choice is kept in `localStorage`, never a cookie.** Keys: `palette` (visitor picks), `palette-last` (rotation), `theme` (`light` or `dark`; absent means match the device). A new visit for rotation is an empty `sessionStorage` key `palette-visit`. A cookie would go to Pages on every request for no purpose and would need a notice; the values are palette ids and a theme name, not personal data. Every read and write is in try/catch; with storage off, the page uses the default palette and the device theme.
- **One inline boot script in `<head>`** (`web/lib/public/boot-script.ts`) sets `data-palette` and `data-theme` on `<html>` before the body is parsed. It reads the owner's choice from attributes the build writes on `<html>` (`data-palette` default, `data-palette-mode`, `data-palettes` enabled ids), so its text is the same on every build and every page. Its SHA-256 is in `EXTRA_SCRIPT_HASHES`; a unit test recomputes it from the text and fails on drift. The build also hashes every inline script it finds, so the page policy lists it either way. No `'unsafe-inline'`.
- **Modes.** Fixed: the default only, a remembered pick is ignored. Rotate: the first visit gets the default, each new visit the next enabled palette in the published order; one palette for the whole visit; no picker. Visitor picks: the remembered palette if still enabled, otherwise the default, with no error.
- **Theme has three states,** device (default), light and dark, on `data-theme`. Palette CSS gives dark values under `@media (prefers-color-scheme: dark)` unless `data-theme="light"`, and always under `data-theme="dark"`. Without JavaScript there is no attribute and the device decides. `color-scheme` follows, so scrollbars and controls match.
- **The menu is one "Theme" disclosure in the nav,** prerendered `hidden` and shown by `DisplayEnhancer`, because nothing can apply a choice without JavaScript. Native radio groups in fieldsets with legends (arrow keys work), 44 px rows, Escape closes and returns focus, a polite live line names the new choice. The palette group is built only in "visitor picks" mode with two or more palettes, and the enhancer removes it if the page says another mode. Swatches are `data-palette` spans, so they take each palette's own tokens with no `style` attribute.
- **`GET /api/v1/site`: `public, max-age=60, s-maxage=120, stale-while-revalidate=60, stale-if-error=604800`,** with a strong ETag (SHA-256 of the body) and 304 on a match. Publish purges the edge; if the purge fails, the edge copy is at most two minutes old, the same as the rebuild debounce in SPEC 7. The edge still answers nearly every read, so the database sees about one read per two minutes per edge location. Images keep `immutable` (random names).
- **Public pages: `public, max-age=0, must-revalidate`** in `_headers` (Pages sends the ETag), so the next page load after a rebuild shows the new palettes. `/_next/static/*` stays `immutable` and `/desk` stays `no-store`; both remove the page value first so no response has two `Cache-Control` headers. The API's admin routes stay `no-store` (default in the headers middleware).
- **Public read cap: 120 requests per minute per client** for `/api/v1/site` and public images together (`PUBLIC_REQUESTS_PER_MINUTE`), 429 with `Retry-After`. The SPEC sets no number; this is far above what a build or a visitor needs once the edge caches. Public reads fail static: with Redis down or unset the cap is skipped and logged, and the read is served. The client is `Cf-Connecting-Ip`, which is only trustworthy once the origin lock rejects traffic that did not come through Cloudflare; until then the edge rate limit is the real layer.
- **Browser tests publish "visitor picks" with presets A, B and E;** the draft stays at the defaults the admin tests expect. The fixed-mode test serves the built home page with `data-palette-mode="fixed"`, which is exactly what a fixed build differs by; the markup rule (no picker unless picks) has its own unit test.

## Phase 3B: section transitions, showcase layouts, project pages and the skills strip

SPEC sections used: 3.9a, 4.3, 4.4, 4.6, 4.8, 4.9, 4.10, 12, 14, 17.

- **`client_key` reads `Cf-Connecting-Ip` only if it parses as an IP address** (`ipaddress.ip_address`); a missing or malformed value falls back to `REMOTE_ADDR`, so a client cannot pick a fresh rate-limit key per request by sending any string. The header is still only fully trustworthy once the origin lock (Phase 7) rejects traffic that did not come through Cloudflare; until then a direct caller can still name any real address.
- **The showcase layout is the existing `showcase_layout` setting** (`ring`, `vertical`, `stack`, `train`; default `ring`, SPEC 17), with `layout_switcher` for the optional visitor switcher. Both have been in the settings shape, the draft and Publish flow and the server validation since 2B, so no migration was needed. New API tests check that each layout reaches `GET /api/v1/site` only after Publish and that unknown values are refused.
- **Section transitions are gated by a script, not only by CSS.** `lib/public/motion.ts` marks sections below the fold as `data-reveal="pending"` and an IntersectionObserver moves them to `in`; the stylesheet hides a pending section only under `prefers-reduced-motion: no-preference`. Without the script, with reduced motion or when printing, nothing is ever hidden. A section that takes focus or is the target of a jump is set to `now` (shown at once, no transition), so focus never lands in a hidden or half-drawn section. The effect is a sheet tilting back into place (perspective `rotateX(-8deg)` and a 48 px rise; tilting away keeps it inside the page width). Cross-page view transitions use `@view-transition` under the same media rule.
- **The hero has the sections' scroll margin,** so its snap point is the top of the page; otherwise Chrome re-snapped the page 62 px down when the script changed the layout. The skills strip is a named region but not a snap point.
- **Showcase positions are a `data-offset` attribute (-3 to 3) per card,** mapped to transforms in the stylesheet, so nothing writes a style. Ring and Vertical count offsets round the ring; Stack and Train count in a line. The deck has perspective but not `preserve-3d`, so cards are drawn in z-index order and a side card never cuts through the front one. Only the front card is in the accessibility tree and the Tab order (`aria-hidden` and `tabindex="-1"` on the others); side cards are not `inert` because a click on one must bring it forward. A card shows at once and hides after its fade, so it can take focus mid-move.
- **3D only over 760 px with a fine pointer and no reduced-motion preference.** 760 to 1000 px shows one side card each way (SPEC 4.9); SPEC 3.9a's "under 1000 px" carousel was read as the phone rule, since 4.9 gives the three breakpoints explicitly. Otherwise the deck is a flat scroll-snap carousel with a peek of the next card and the same controls; this is the static version of every layout under reduced motion.
- **Controls:** previous and next buttons, a "01 / 08" counter (`aria-hidden`) with a polite status line that reads "Project 2 of 8: title", one 24 px button per project with `aria-current`, arrow keys (up and down too in Vertical), and swipe. All controls are prerendered `hidden` and shown by the script.
- **The detail sheet is a native `<dialog>`** filled with a copy of the front card plus a "Full case study" link; ids are stripped from the copy. Close by button, Escape or a click outside; focus returns to the card. The URL becomes `#project-<slug>` while it is open and opening the page with that fragment opens it. Each card in the showcase also carries the project's label/value fields and links, which the plain list shows without JavaScript and the 3D deck leaves to the sheet.
- **Not built: moving through projects by scrolling past a pinned section** (SPEC 3.9a). It is one of several ways to move, the others all work, and a scroll-linked deck would fight the keyboard state and scroll snapping. Revisit if the owner wants it.
- **`/projects` is split six to a page** (the SPEC gives no size): `/projects`, then `/projects/page/2` onwards, each a static page with its own canonical, `rel` previous and next, numbered links and `aria-current="page"`. Canonicals are paths for now; the site origin arrives with SEO in 3C. A static export must build at least one page for the route, so with one page of projects `/projects/page/2` is built as a `noindex` page saying it does not exist. Any other missing page is the 404 page, which now links to the list. No project may take the slug `page`.
- **The skills strip** is real text with an accessible name. Without JavaScript it is a static wrapping list. The script adds a copy for the seamless loop (`aria-hidden` and `inert`), a Pause/Play button and a polite status line; hover and focus inside pause it in CSS. Under reduced motion it starts paused, and the global reduced-motion reset makes one exception so the visitor's Play still works.
- **One client component, `HomeEnhancer`,** runs the three home scripts; no animation library. Initial JavaScript on home is 146.4 kB gzipped on the browser-test build (136.4 kB modules, 10.0 kB inline payload with eight projects), under the 150 kB budget. The inline payload grows with each published project; this needs a CI check before many more projects are added.
- **Browser tests seed eight projects and turn the layout switcher on,** so every layout and the second list page are tested.

## Phase 3C: SEO, error and footer pages, carried-over fixes, test matrix and section navigation

SPEC sections used: 3.9a, 3.10, 4.4, 4.6, 4.8, 4.9, 4.10, 8.1 to 8.5, 9.3, 12.1, 17.

- **Initial JavaScript is checked on every build** by `check:export` (`lib/js-budget.ts`): the scripts each public page loads at first paint (not the legacy `nomodule` copy) plus its inline scripts, gzipped, in kB of 1,000 bytes. Over 150 kB fails; home's figure is printed. The margin was 3.7 kB, so the home motion (section transitions, showcase, skills strip) is now one chunk loaded by a dynamic import after hydration: home went from 146.3 to 143.6 kB on the browser-test build (eight projects). Until it runs the page shows the static versions it already showed without JavaScript, so nothing moves or hides on load; a section is only held back for its transition if it was below the fold when the code ran.
- **The stand-in `/projects/page/2`** that a static export needs when there is one page of projects stays `noindex` with no canonical. The sitemap and every pagination link come from `listRoutes()` and `pageInfo()`, which never name it (unit tests for 0, 1 and 6 projects).
- **Markdown headings follow the page outline.** The first heading in a text takes the level below the heading the text sits under (case study body h3 under the "Case study" h2, case study summary h2 under the h1, card summaries one below the card title, timeline summaries h4), and each heading is at most one level below the one it sits under, whatever levels the source uses; past h6 stays h6. Before, `#` became h3 and every other level h4, so a body starting with `##` skipped h3.
- **A project's slug is stored when it is first published and never changes after** (`section_items.slug`, unique, migration 0012). Publish gives each shown project without a slug one from its title at that moment, with -2, -3 on a clash and never `page`; a rename, a hide, the trash and a restore all keep it, and a new project cannot take the slug of one in the trash. Delete for good frees it. The published copy of each item carries its slug, so `GET /api/v1/site` sends it and the web build uses it (falling back to a title slug only for an item without one). Migration 0012 gives every existing project a slug, live ones first in site order from their published titles so current addresses stay the same, then the rest from their draft titles, and writes the slugs into the published copies. The slug rules live in `core/slugs.py` and `slugify()` in the web app; `api/tests/slug_vectors.json` is checked by both test suites. /desk shows each project's address under its title.
- **Pinned-scroll movement is removed from the SPEC (3.9a),** not left as "not built". Moving the showcase as the page scrolls takes the scroll away from the visitor, which is scroll-jacking in effect, and it is bad for keyboard, switch and screen-magnifier users, who lose their place. Buttons, arrow keys, dots and swipe already cover navigation. SPEC 3.9a now also agrees with 4.9 and with what is built: 3D from 760 px with a fine pointer and no reduced motion, one side card each way from 760 to 1000 px, the full layouts over 1000 px.
- **`SITE_ORIGIN` is the one public address,** the same name the API already uses for the site's origin. `lib/seo.ts` checks it when `next.config.ts` loads: a Pages build (`CF_PAGES`) without it, or with anything but an https origin with no path, fails at once with the reason; any other build may leave it out and gets `http://localhost:3000` (the browser tests set `http://localhost:3100`). `check:build-refuses` proves the Pages case fails. Every canonical, `og:url`, the sitemap and robots.txt are built from it.
- **Titles and descriptions** come from the owner's `settings.seo` entries (home, projects, privacy, security, how_built; accessibility has none yet and uses its fallback), then the site description, the hero text or the project summary, then a plain fallback ("Projects by <name>."). TODO markers are never used as a description. Markdown is turned into plain text and cut at a word to 155 characters.
- **One static preview image,** `public/og-default.png` (1200 by 630, flat preset A colours, the owner's name in the site's display face), for Open Graph and Twitter cards. SPEC 8.2 asks for images generated at build time; per-page images would need a new rendering step for little gain, and the settings have no owner-chosen image yet. When one exists the metadata helper is the one place to use it.
- **The sitemap and robots.txt are Next metadata files** built with the static export (`app/sitemap.ts`, `app/robots.ts`), so no route handler or server is involved. The sitemap lists home, the list pages that exist, each project and the footer pages; never `/desk`, the 404 page or the page built past the end. robots.txt allows everyone, asks a named list of AI training crawlers and bulk scrapers to stay away (SPEC 8.5; a request, enforced by Cloudflare), and names the sitemap. `/desk` is not disallowed: a disallowed page can still be indexed from links, while its `X-Robots-Tag: noindex` and `no-store` keep it out.
- **JSON-LD:** a `Person` block on home and a `CreativeWork` block on each case study (SPEC 8.2), as `<script type="application/ld+json">`. A data block is never run, and CSP `script-src` does not apply to it, so it needs no hash: `lib/pages-headers.ts` leaves it out of the policy and the policy is unchanged otherwise. Its JSON escapes `<`, `>`, `&` and the two line separators, so no text can end the element. A browser test checks each block parses, is not in the policy and causes no CSP report.
- **`check:export` checks every page:** exactly one `<title>`; a page open to search has exactly one canonical (absolute, on `SITE_ORIGIN`, pointing at the page itself), one description, `og:url` equal to the canonical, an `og:image` and a large Twitter card, and is in the sitemap; a page kept out of search (404, `/desk`, the page built past the end) has no canonical and is not in the sitemap; home has exactly one JSON-LD `Person`; robots.txt names the sitemap.
